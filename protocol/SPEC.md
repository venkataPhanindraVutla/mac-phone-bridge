# Android Mirroring Protocol, version 1

This document specifies the protocol spoken between the Mac app and the Android app.
It is written so that anyone can build a compatible client or server. The schema lives in
`protocol/proto/anmirror/v1/*.proto`; test vectors live in `protocol/vectors/*.json` and are
generated by `protocol/tools/make_vectors.py`, which is also a reference implementation of
the framing, crypto and pairing-URI rules below. If this text and the vectors disagree, that
is a bug: please report it.

Key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Transport

- TCP carrying **mutual TLS 1.3**. Anything below TLS 1.3 MUST be rejected.
- The **Mac is the TLS server**, the **phone is the TLS client**. Both present a certificate;
  both sides require the peer's certificate.
- Certificates are self-signed. Trust is never based on a CA. Instead each side **pins the
  peer's certificate by fingerprint** (section 3). A certificate whose fingerprint is not
  the expected one MUST be rejected.
- Discovery uses Bonjour/mDNS service type `_anmirror._tcp`. The advertisement carries no
  personal data: a random instance name and two TXT keys, `v` (protocol version, `1`) and
  `r` (rotating ID, section 6). The Mac picks a new random instance name at every 15-minute
  epoch and on wake from sleep; the phone finds its Mac by TXT `r` only, never by the name.
- A Mac serves one phone at a time. A phone connects to one Mac at a time.

## 2. Framing

Every message is one **frame**:

```
+----------------------+---------------------------+
| length (4 bytes, BE) | Envelope (protobuf bytes) |
+----------------------+---------------------------+
```

- `length` is an unsigned 32-bit big-endian integer, the byte length of the Envelope that follows.
- `length == 0` is an error (`emptyFrame`).
- `length > 1,048,576` is an error (`frameTooLarge`). The receiver MUST detect this from the
  header alone, without reading the body, and MUST close the connection.
- `length == 1,048,576` is valid and `1,048,577` is too large. This boundary is not in the
  vectors because of the frame's size.
- Either error closes the connection.

Vectors: `vectors/framing.json`. `vectors` entries give the envelope fields and the exact
frame bytes; `invalid` entries give a frame prefix and the expected error.

Serialization notes for implementers who encode by hand: this is proto3, so fields equal to
their default value (0, empty string, empty bytes, false) are omitted, and fields are written
in ascending field-number order. Negative `int32` values (for example `signal_level = -1`)
are encoded as 10-byte sign-extended varints.

## 3. Envelope and message types

```proto
message Envelope {
  Channel channel = 1;
  uint64 id = 2;
  uint64 reply_to = 3;
  string type = 4;
  bytes payload = 5;
}
```

- `id` counts up from 1, per sender, per connection.
- `reply_to` carries the `id` of the request being answered, or 0.
- `type` names the message in `payload`, serialized as protobuf.
- Receivers MUST ignore messages with an unknown `type` on a known channel (forward
  compatibility), and MUST ignore unknown protobuf fields. Exception: section 5.4 takes precedence on an unpaired
  connection, where the first message must be `pairing.request`, else `system.error NOT_PAIRED`
  (an unknown `type` there is not ignored).

### Capabilities

`Hello.capabilities` lists feature strings the sender supports. Version 0.1 defines
`status.v1` and `find.v1`. Version 0.2 adds `notify.v1`, `contacts.v1` and `calls.v1`
(sections 10 to 12). Version 0.3 adds `clipboard.v1`, `share.v1`, `files.v1`,
`screenshots.v1`, `photos.v1` and `browse.v1` (sections 13 to 19).
Version 0.4 adds `media.v1`, `dnd.v1`, `proximity.v1` and `input.v1` (sections 20 to 23). A side MUST NOT send messages of a feature the peer did not list.

`Hello.protocol_version` is the integer **1**. If versions differ, the receiver answers
`system.error` with `ERROR_CODE_PROTOCOL_MISMATCH` and closes.

## 4. Identity and fingerprints

- Each device owns a self-signed certificate and its private key (any key type TLS 1.3
  accepts; the reference apps use EC P-256).
- **Fingerprint:** `fp = SHA-256(certificate DER)`, 32 raw bytes. It is displayed and stored as
  **lowercase hex** (64 characters). The **device ID** is that hex string.

## 5. Pairing

### 5.1 Definitions

- The **pairing secret** is 32 random bytes generated by the Mac for each pairing window. It
  is **single-use** and **expires 5 minutes** after creation.
- **Secret proof:** `HMAC-SHA256(key = secret, msg = "anmirror-pair-v1" || mac_fp || phone_fp)`,
  where `||` is byte concatenation, the label is its ASCII bytes, and `mac_fp`, `phone_fp`
  are the 32 raw fingerprint bytes.
- **Confirmation code** (shown on both screens so the user can compare them):
  - `h = SHA-256("anmirror-sas-v1" || mac_fp || phone_fp)`
  - `code = uint32_be(h[0..4]) mod 1,000,000`, rendered as exactly 6 digits, **zero-padded**
    (for example `097702`). In vectors the code is therefore a JSON string.
- **Discovery key:** 32 random bytes generated once per Mac and sent to the phone in
  `PairComplete`. It is used for the rotating ID (section 6).

Vectors: `vectors/crypto.json` (`fingerprints`, `proofs`, `codes`). Fingerprints are computed
over the DER of the three committed test certificates (`protocol/testdata/identities`); each
entry has a `name` (`mac`, `phone`, `stranger`). The `codes` set includes a vector whose code
has a leading zero.

### 5.2 Pairing URI (QR code content)

```
anmirror://pair?v=1&fp=<b64url(mac_fp)>&s=<b64url(secret)>&h=<host>,<host>&p=<port>&n=<pct(mac_name)>
```

- `b64url` is RFC 4648 section 5 (URL-safe alphabet), **no padding**. Padding characters and
  the standard alphabet (`+`, `/`) are rejected.
- `pct` is RFC 3986 percent-encoding of the UTF-8 bytes; the unreserved characters
  (`A-Z a-z 0-9 - . _ ~`) are kept, everything else is `%XX` (uppercase hex).
- `h` is a comma-separated list of one or more hosts (IPv4 addresses or hostnames), in the
  order the phone should try them. Hosts MUST NOT contain `,` or `&`.
- `p` is the TCP port, `1..65535`. `n` is optional (empty name if absent).
- **Parsing:**
  - The URI MUST start with `anmirror://pair?`; otherwise `malformed`.
  - Unknown extra parameters are **ignored**.
  - A repeated parameter is `malformed`.
  - `v` and `p` MUST fully match ASCII `0|[1-9][0-9]*` (canonical decimal: no sign, no leading
    zeros, no non-ASCII digits such as `²`); otherwise `malformed`. So `v=01` and `p=049152`
    are `malformed`.
  - `v` missing or not canonical is `malformed`; `v` other than 1 is `unsupportedVersion`.
    The version is checked before any other field, so a `v=2` URI is `unsupportedVersion`
    even if its other fields would not parse.
  - b64url values must be **canonical**: re-encoding the decoded bytes must give the original
    text, i.e. the unused trailing bits of the last character must be zero.
  - `fp` or `s` missing, not valid (canonical) b64url, or not decoding to exactly 32 bytes: `malformed`.
  - `h` missing or containing an empty entry, `p` missing or out of range: `malformed`.
  - `n`: an escape is `%` followed by **exactly two** characters from `[0-9A-Fa-f]`; anything
    else (`%+1`, `% 1`, `%G1`, a trailing `%4`) is `malformed`, as is a raw non-ASCII character
    or a result that is not valid UTF-8.
- The phone tries the hosts in order, each with a 3 s connect timeout.

Vectors: `vectors/pairing_uri.json`. Each `valid` entry has the URI and the parsed `fields`
(`version`, `fp_hex`, `secret_hex`, `hosts`, `port`, `mac_name`); each `invalid` entry has the
URI and the expected error (`malformed` or `unsupportedVersion`). They include a name with a
curly apostrophe and an emoji (`Ada’s MacBook Pro 🍎`) and two hosts.

### 5.3 Sequence

The phone scans the QR code, then connects as TLS client and **pins `fp` from the QR code** as
the Mac's identity. The Mac accepts the phone's (unknown) certificate only while a pairing
window is open and its secret can still be used: not yet used, not burned by 3 bad proofs, and
at most 5 minutes old. Afterwards an unknown certificate is refused during the TLS handshake,
which the phone shows as "code expired".

1. Phone sends `pairing.request{protocol_version, secret_proof, device_name, device_model}`.
   If the protocol version is wrong, the Mac replies `system.error PROTOCOL_MISMATCH`.
2. The Mac computes the expected proof from its own fingerprint and the phone certificate's
   fingerprint, and compares in constant time.
   - Match: Mac sends `pairing.verified`.
   - Mismatch: `system.error BAD_PAIRING_SECRET`.
   - After **3** bad proofs, or when the secret has already been used, or is **5 minutes old**:
     `system.error PAIRING_EXPIRED`.
3. Both sides compute and show the **confirmation code**.
4. Each side sends `pairing.confirm{accepted}` when its user decides. `accepted = false` from
   either side means both show "Pairing cancelled" and the connection closes. Each side waits
   at most **60 s** for the user's decision.
5. When both sides have accepted, the Mac sends `pairing.complete{discovery_key, mac_name}`.
   Both sides persist the peer (device ID = fingerprint hex). The secret is now spent.
6. The phone then sends `system.hello` on the same connection.

`PAIRING_REJECTED` is sent when a side refuses to continue pairing for a reason other than a
user decline (for example the Mac's pairing window was closed).

### 5.4 Rules after pairing

- An **unpaired client certificate** is accepted only while a pairing window with a usable
  secret is open (section 5.3), and its first message MUST be `pairing.request`. Anything else gets `system.error NOT_PAIRED`, then
  the connection is closed.
- A **second paired phone** connecting while one is active gets `system.error BUSY`, then the
  connection is closed.
- Unpairing from either side sends `system.goodbye{UNPAIRED}`; a phone that moves to another
  Mac sends `SWITCHING_MAC`; an orderly quit sends `SHUTDOWN`.

## 6. Reconnection and rotating ID

A phone may find its Mac again by Bonjour without any personal data being advertised. The Mac
publishes TXT `r`, a rotating ID derived from the discovery key:

- `epoch = floor(unix_seconds / 900)` (15-minute epochs)
- `r = lowercase hex of HMAC-SHA256(key = discovery_key, msg = "anmirror-rid-v1" || uint64_be(epoch))[0..8]`
  (the first 8 bytes, so 16 hex characters)
- The phone accepts `epoch - 1`, `epoch` and `epoch + 1`, to tolerate clock skew.
- The Bluetooth advertisement of section 22 uses the same epoch with its own ID (the BLE ID).

Vectors: `vectors/crypto.json` `rotating_ids` (each entry also lists the `epoch`, and includes
values on both sides of an epoch boundary).

## 7. Keep-alive and lifecycle

Initial values (battery tuning is planned for 0.9):

- The phone sends `system.ping` every **30 s**. If no `system.pong` arrives within **10 s**,
  the phone drops the connection and reconnects.
- The Mac marks the phone as lost after **75 s** with no incoming message.
- On wake from sleep the Mac closes every connection and restarts its listener on the same port.
- When the Mac app quits it sends `system.goodbye{SHUTDOWN}` to the connected phone first. The
  phone treats it as a normal disconnect: it keeps the pairing and reconnects with its backoff.

What the user sees (builder's call, recorded in 0.1; shorter detection is tracked for 0.9):
"connected/disconnected" updates **immediately when the connection closes** (app quit, Mac
sleep/wake, phone app stopped), and **within 75 s when the phone vanishes** (Wi-Fi off, out of
range), which is the Mac's silence timeout above.

## 8. Errors

`system.error` carries an `ErrorCode` and a human-readable English `message` intended for logs,
not for display. Codes: `PROTOCOL_MISMATCH`, `NOT_PAIRED`, `BAD_PAIRING_SECRET`,
`PAIRING_EXPIRED`, `PAIRING_REJECTED`, `BUSY`. After `system.error` in the situations above the
sender closes the connection. Framing errors (section 2) close the connection without a reply.

## 9. Regenerating vectors and test identities

- `python3 -I protocol/tools/make_vectors.py` writes `protocol/vectors/*.json`;
  `... --check` regenerates in memory and exits 1 on any difference. The output is
  deterministic; the only external input is the committed test certificates, which are read
  with `openssl`, so **`--check` needs `openssl` on PATH** (a missing one exits 2 with a message).
- `scripts/make-test-identities.sh` creates the three test-only PKCS#12 identities (password
  `test`). **Re-running it creates new keys, which changes the fingerprints**, so the vectors
  must be regenerated and every implementation's tests re-run. The identities are for tests
  only and never ship in any app.

## 10. Notifications (`notify.v1`)

Channel `NOTIFY`. Messages are listed in section 3.

- `PhoneNotification.key` is the Android `StatusBarNotification.key`. The Mac replaces its
  notification by key.
- `alert = false` means "update silently": the Mac refreshes the content without alerting.
- On connect, the phone sends each still-active, eligible notification that this Mac has not
  received during this phone process, or whose title, text or actions changed since this Mac
  last received it, all with `alert = false`; then one `notify.snapshot` listing every active
  key. The phone remembers what it sent for the last Mac that connected only, so a different
  Mac gets every active notification. The Mac removes any notification it shows whose key is
  not in the snapshot. If the phone cannot read its active notifications, it sends neither.
- Every `notify.invoke` is answered by one `notify.result`: `OK` on success, `GONE` or `FAILED`
  otherwise. It carries `reply_to` set to the invoke's `id` and an `ActionOutcome`. The Mac does
  not retry.
- `notify.filter` is sent by the Mac after every connect and on every settings change. The
  phone sends nothing for muted packages, or for anything at all when `enabled = false`.
- Icons go request to response (`notify.icon_request`, `notify.icon`), once per package per
  Mac cache.
- `notify.availability` reports whether the feature works on the phone: `enabled` and, when
  not, a `reason`: `OFF_BY_USER`, `NEEDS_PERMISSION`, `PARTIAL_ACCESS`, `UNAVAILABLE` (this device
  cannot do it at all) or `NEEDS_SETUP` (the user must set something up first). It is sent on connect
  and on change. `dnd.availability` and `input.availability` also go from Mac to phone.
- Wire limits:
  - `image_jpeg`: long edge at most 720 px, at most 300 KB; dropped if it does not fit.
  - `AppIcon.png`: 96x96, at most 32 KB.
  - `title` at most 256 bytes, `text` at most 4,096 bytes, `sub_text` at most 256 bytes, each
    cut at a UTF-8 character boundary with "…" appended when cut.

## 11. Contacts (`contacts.v1`)

Channel `CONTACTS`.

- `ContactsSyncRequest.since_ms` is the phone's `CONTACT_LAST_UPDATED_TIMESTAMP` high-water
  mark, taken from the `sync_ms` of the last batch the Mac received; `0` asks for a full sync.
- Batches hold at most 200 contacts. A `full = true` sequence replaces the Mac's whole store
  when the batch with `last = true` arrives; until then the old store stays in use.
- While connected, the phone pushes `full = false` batches on change, debounced by 5 s.
  `deleted_ids` lists removed contacts.
- `contacts.availability` is as in section 10.

## 12. Calls (`calls.v1`)

Channel `CALLS`.

- `CallState.call_id` is a random UUID per call, made by the phone.
- `calls.state` is sent on every phase or mute change, and on connect if a call is in
  progress. `ENDED` is sent once per call.
- `can_answer` is true only when the phone can answer that call; `mute_supported` says whether
  muting works.
- `calls.command` is answered by `calls.result` with `reply_to` set to the command's `id`.
  A command for a call that is not (or no longer) in progress gets `NO_SUCH_CALL`.
- `calls.missed` is sent when a call rang, was never answered, and was not declined through
  `calls.command` (confirmed with the call log, type `MISSED`, where available).
- `calls.availability` is as in section 10.

## 13. Bulk connections

File bytes never travel in control frames. They use separate bulk connections.

- The Mac runs a second TLS 1.3 listener on an ephemeral port, with the same pinning as
  section 1. It accepts only the certificate of the connected, paired phone.
- The Mac announces the port with `files.endpoint` right after connect, whenever any of
  `files.v1`, `screenshots.v1`, `photos.v1` or `browse.v1` is shared.
- The phone always dials. Its first frame is a normal section 2 frame whose envelope is
  `{channel FILES, id 1, type "bulk.hello"}` carrying `BulkHello`.
- Tokens are issued by the Mac only: in `files.offer` when the Mac sends, in `files.accept`
  when the Mac receives, and in `photos.thumbs`. A token is 32 random bytes, single-use, and
  expires after 60 s.
- An unknown, expired or reused token, or a role that does not match the token, closes the
  connection without a reply.
- After the hello, the sender writes exactly `size` raw bytes. The receiver reads exactly
  `size` bytes and never waits for EOF; extra bytes fail the transfer. The sender closes after
  `files.received` or `files.failed`, or after 30 s.
- A control disconnect revokes every token and ends every bulk connection.
- Requests that the Mac originates (`photos.list`, `browse.*`) carry their own `request_id`, a
  Mac counter echoed by the phone, not the envelope `reply_to`.

## 14. Clipboard (`clipboard.v1`)

Channel `CLIPBOARD`. Plain text only, at most 262,144 bytes, in both directions. Concealed,
transient and auto-generated pasteboard items are never sent. Neither side sends back text whose
SHA-256 equals the last text it received from the peer. `clipboard.availability` is as in
section 10.

## 15. Share (`share.v1`)

Channel `SHARE`.

- `share.link` is only for `http` or `https` URLs with a host, at most 8,192 bytes. Anything
  else is sent as `share.text`.
- The receiver opens the link (on the phone, after a tap on a notification).
- `share.text` lands on the clipboard, with a notification.
- Files are section 16 transfers.

## 16. Files (`files.v1`)

Channel `FILES`. `files.*` messages are the transport for `files.v1`, `browse.v1` (reads and writes),
`screenshots.v1` and `photos.v1`; a side may send them when the feature the transfer serves is shared.

- **Steps.** `files.offer`, then `files.accept` or `files.reject`, then the bulk bytes
  (section 13). During the bytes the receiver sends `files.progress` (at most every 500 ms).
  When the bytes are written the sender sends `files.complete` with the SHA-256. The receiver
  answers `files.received`, or `files.failed` with `HASH_MISMATCH`.
- **Cancel.** Either side may send `files.cancel`. No reply is sent.
- **Queueing.** One transfer at a time per direction; the next offer waits until the previous
  transfer has ended.
- **Auto-accept.** Offers from the paired peer are accepted automatically; both devices belong
  to the same user.
- **Free space.** The receiver rejects an offer with `NO_SPACE` when `size + 64 MiB` exceeds
  the free space.
- **No resume.** An interrupted transfer starts again from the offer.
- **File-name rule**, applied by the receiver to `TransferOffer.name`:
  1. Take the text after the last `/` or `\`.
  2. Remove C0 controls, DEL (U+007F) and the bidi controls U+202A to U+202E and U+2066 to
     U+2069.
  3. Strip leading dots and spaces and trailing spaces.
  4. If nothing is left, use `file`.
  5. Cap at 255 bytes of UTF-8, cutting the stem at a Unicode scalar boundary and keeping an
     extension (the text from the last `.`, dot included) of at most 16 bytes. After any cut,
     strip trailing spaces and dots from the cut stem (or from the whole name when there is no
     extension), so step 3 still holds.
  6. Collisions are case-insensitive and normalization-insensitive: two names collide when
     `key(name) = lowercase(NFC(name))` is equal, where NFC is Unicode normalization form C and
     `lowercase` is the Unicode default lowercase mapping, independent of locale (Python
     `unicodedata.normalize("NFC", s).lower()`, Kotlin
     `Normalizer.normalize(s, Normalizer.Form.NFC).lowercase(Locale.ROOT)`, Swift
     `s.precomposedStringWithCanonicalMapping.lowercased()`). On a collision, use
     `stem (n).ext` with the smallest free `n >= 1` (keys compared), still within the 255-byte
     cap (the stem is cut further, and re-stripped as in step 5, when needed).

  `protocol/vectors/filenames.json` holds reference cases generated by `make_vectors.py`.

## 17. Screenshots (`screenshots.v1`)

Channel `SCREENSHOTS`. The phone sends `TRANSFER_KIND_SCREENSHOT` offers over section 16.
`screenshots.availability` is as in section 10 and may carry `PARTIAL_ACCESS`, which means new
screenshots cannot be found.

## 18. Photos (`photos.v1`)

Channel `PHOTOS`.

- `photos.list` (`limit` 1 to 200) is answered by `photos.items`, newest first.
- `photos.thumbs` is answered over one bulk connection with role `THUMBNAILS`. Each record is
  `uint64_be id | uint32_be length | JPEG`, in request order. A length of 0 means no thumbnail;
  a length over 1 MiB is an error. The stream ends with the record `id = 0, length = 0`.
- `photos.fetch` is answered by a `TRANSFER_KIND_PHOTO` offer carrying its `request_id`, or by
  `files.failed` with that `request_id` and `NOT_FOUND`.
- `PARTIAL_ACCESS` (in `photos.availability` and `PhotosList.partial_access`) means the list
  holds only the items the user picked.

## 19. Browse (`browse.v1`)

Channel `BROWSE`.

- **Paths** are relative to a root and `/`-separated; `""` is the root itself. A segment that
  is empty, `.` or `..`, or contains `\0`, a path with a leading `/`, or a path over 4,096
  bytes, is `BAD_PATH`. Symlinks that resolve outside the root are neither listed nor followed.
- **Listing.** `browse.list` pages are sorted directories first, then by name
  (case-insensitive), with `limit` clamped to 1 to 500.
- **Deleting** is recursive and never follows symlinks.
- **Renaming.** `new_name` must equal its own sanitized form (section 16), else `BAD_PATH`.
- **Reading.** `browse.read` is answered by a `TRANSFER_KIND_FILE` offer with its `request_id`,
  or by `browse.result` with the failure.
- **Writing.** A write is a Mac `files.offer` with `target`. With `overwrite = false` a
  collision gets the section 16 counter.
- **Revoked folders.** A picked folder whose permission was revoked answers `REVOKED`, and the
  phone pushes an updated `browse.roots`.
- `browse.availability` is as in section 10.

## 20. Media (`media.v1`)

Channel `MEDIA`.

- The phone reports the session it picks: the one in `STATE_PLAYING` (the most recently started
  if several), else the most recently active.
- It sends `media.state` on change, at most 4 per second (leading and trailing edge), and right
  after connect. `active = false` means nothing is playing, and every other field is empty.
- `position_ms` is the position at send time. While `playing`, the Mac extrapolates with its own
  clock at `speed` (1.0 when the speed is 0).
- `media.artwork` is sent before the first `media.state` that names its key, and sent once per key
  while it is among the 8 most recently sent keys; the Mac keeps those 8 (in memory, cleared on
  disconnect). A key that has dropped out of the 8 is sent again. It is a JPEG, long edge 300 px,
  at most 98,304 bytes; artwork that does not fit is not sent and the key is empty.
- The artwork key is the lowercase hex of the first 8 bytes of SHA-256 over the JPEG bytes.
- `media.command` names a `session_key`. A command for any other key is ignored. A command whose
  action the state does not offer (for example `SEEK` without `can_seek`) is ignored.
- `SET_VOLUME.volume` is in the phone's own steps, `0..volume.max`. It is ignored when `fixed`.
- The text limits are as in section 10 (256 bytes each).
- `media.availability` is as in section 10.

Vectors: `framing.json` `media_state_minimal`; `crypto.json` `artwork_keys`.

## 21. Do Not Disturb (`dnd.v1`)

Channel `DND`.

- "On" means the phone's interruption filter is anything but ALL, or the Mac has any Focus on.
- Each side sends transitions only (`snapshot = false`) while its own `sends` is enabled and the
  peer's last `applies` is enabled (nil = off).
- **Availability.** Phone `sends` = the switch is on; phone `applies` = the switch is on and the
  Do Not Disturb policy access is granted. Mac `sends` = the setting is on and Focus status is
  readable; Mac `applies` = the setting is on and both Shortcuts are installed.
- Right after connect it also sends one `snapshot = true` state, whenever its `sends` is enabled.
  A snapshot is shown, never applied.
- **Applying.** A side applies a peer transition only when `origin = USER`, and only if its own
  state differs. It then remembers (state, time).
- **Echoes.** A local transition to that state within 10 s is not sent. A later one that matches
  the last applied state, with no other local transition in between, is sent with
  `origin = SYNC`. `SYNC` states are never applied. Example: the Mac turns Focus on and the phone
  applies it. If the phone's filter then reports "on" within 10 s, that is the echo and nothing is
  sent. If that "on" only shows up after 10 s, with no other local transition before it, it is
  sent with `origin = SYNC`. Any local transition ends the match: if the user turns the phone's
  filter off and on again, the "off" and the second "on" are both sent with `origin = USER`.
- `dnd.availability` is sent both ways on connect and on change.

## 22. Proximity (`proximity.v1`)

Channel `PROXIMITY`.

- The BLE ID is `HMAC-SHA256(key = discovery_key, msg = "anmirror-ble-v1" || phone_fp || uint64_be(epoch))[0..8]`
  (the first 8 bytes), with the epoch of section 6. `phone_fp` is the 32-byte SHA-256 certificate
  fingerprint of the paired phone, raw bytes (section 4). The Mac computes one ID per paired phone.
- **The advertisement** is legacy (31-byte limit), non-connectable, without the device name or TX
  power, and its only element is the service data: UUID `3d30288c-0f47-4016-a6ba-44506f920431` and the 8 bytes of the
  BLE ID. The phone restarts it at each epoch.
- The Mac accepts `epoch - 1` to `epoch + 1`.
- `proximity.availability` says whether the phone is advertising. It is not a protocol message
  over BLE.
- No personal data is advertised.

Vectors: `crypto.json` `ble_ids`, with values on both sides of an epoch boundary and for two
different phone fingerprints.

## 23. Input (`input.v1`)

Channel `INPUT`.

- The phone sends `input.*` only while the Mac's last `input.availability` is enabled.
- `input.move` and `input.scroll` are relative, in Mac points. A scroll is the finger's movement;
  the Mac applies its Natural scrolling setting.
- The phone coalesces moves and scrolls to at most 120 Hz: deltas are summed, never queued.
- `input.click.count` is the click count (2 = double-click).
- A button held 5 s after the last `input.*` frame, or at disconnect, is released by the Mac, and
  the laser is hidden.
- While a button is held or the laser is on, the phone repeats that frame after any 2 s in which
  it sent nothing else (`input.button{down: true}` for each held button, `input.laser{on: true}`). A `down` for the
  button the Mac already holds only counts as a frame; `laser{on: true}` shows the dot again if it
  was hidden.
- The Mac drops frames beyond 240 in any 1 s window, except button-up and laser-off.
- `REMOTE_KEY_PREV_SLIDE` and `REMOTE_KEY_NEXT_SLIDE` are the Left and Right arrow keys.

Vectors: `framing.json` `input_move`.
