# Android Mirroring Protocol, version 1

This document specifies the protocol spoken between the Mac app and the Android app.
It is written so that anyone can build a compatible client or server. The schema lives in
`protocol/proto/anmirror/v1/*.proto`; test vectors live in `protocol/vectors/*.json` and are
generated by `protocol/tools/make_vectors.py`, which is also a reference implementation of
the framing, crypto and pairing-URI rules below. If this text and the vectors disagree, that
is a bug: please report it.

Key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Transport

- TCP carrying **mutual TLS 1.3**. Anything below TLS 1.3 MUST be rejected.
- The **Mac is the TLS server**, the **phone is the TLS client**. Both present a certificate;
  both sides require the peer's certificate.
- Certificates are self-signed. Trust is never based on a CA. Instead each side **pins the
  peer's certificate by fingerprint** (section 3). A certificate whose fingerprint is not
  the expected one MUST be rejected.
- Discovery uses Bonjour/mDNS service type `_anmirror._tcp`. The advertisement carries no
  personal data: a random instance name and two TXT keys, `v` (protocol version, `1`) and
  `r` (rotating ID, section 6).
- A Mac serves one phone at a time. A phone connects to one Mac at a time.

## 2. Framing

Every message is one **frame**:

```
+----------------------+---------------------------+
| length (4 bytes, BE) | Envelope (protobuf bytes) |
+----------------------+---------------------------+
```

- `length` is an unsigned 32-bit big-endian integer, the byte length of the Envelope that follows.
- `length == 0` is an error (`emptyFrame`).
- `length > 1,048,576` is an error (`frameTooLarge`). The receiver MUST detect this from the
  header alone, without reading the body, and MUST close the connection.
- `length == 1,048,576` is valid.
- Either error closes the connection.

Vectors: `vectors/framing.json`. `vectors` entries give the envelope fields and the exact
frame bytes; `invalid` entries give a frame prefix and the expected error.

Serialization notes for implementers who encode by hand: this is proto3, so fields equal to
their default value (0, empty string, empty bytes, false) are omitted, and fields are written
in ascending field-number order. Negative `int32` values (for example `signal_level = -1`)
are encoded as 10-byte sign-extended varints.

## 3. Envelope and message types

```proto
message Envelope {
  Channel channel = 1;
  uint64 id = 2;
  uint64 reply_to = 3;
  string type = 4;
  bytes payload = 5;
}
```

- `id` counts up from 1, per sender, per connection.
- `reply_to` carries the `id` of the request being answered, or 0.
- `type` names the message in `payload`, serialized as protobuf.
- Receivers MUST ignore messages with an unknown `type` on a known channel (forward
  compatibility), and MUST ignore unknown protobuf fields.

| `type` | Direction | Payload | Channel |
|---|---|---|---|
| `system.hello` | both (phone first) | `Hello` | SYSTEM |
| `system.ping` / `system.pong` | phone to Mac / reply | `Ping` / `Pong` | SYSTEM |
| `system.error` | either | `Error` | SYSTEM |
| `system.goodbye` | either | `Goodbye` | SYSTEM |
| `pairing.request` | phone to Mac | `PairRequest` | PAIRING |
| `pairing.verified` | Mac to phone | `PairVerified` | PAIRING |
| `pairing.confirm` | both | `PairConfirm` | PAIRING |
| `pairing.complete` | Mac to phone | `PairComplete` | PAIRING |
| `status.update` | phone to Mac | `StatusUpdate` | STATUS |
| `find.ring` / `find.stop` | Mac to phone | `RingRequest` / `StopRingRequest` | FIND |
| `find.state` | phone to Mac | `RingState` | FIND |

`status.update.signal_level` is `0..4`, or `-1` for unknown / no service; it is always sent
explicitly (never omitted, which is why `0` and `-1` are distinct on the wire).

### Capabilities

`Hello.capabilities` lists feature strings the sender supports. Version 0.1 defines
`status.v1` and `find.v1`. A side MUST NOT send messages of a feature the peer did not list.

`Hello.protocol_version` is the integer **1**. If versions differ, the receiver answers
`system.error` with `ERROR_CODE_PROTOCOL_MISMATCH` and closes.

## 4. Identity and fingerprints

- Each device owns a self-signed certificate and its private key (any key type TLS 1.3
  accepts; the reference apps use EC P-256).
- **Fingerprint:** `fp = SHA-256(certificate DER)`, 32 raw bytes. It is displayed and stored as
  **lowercase hex** (64 characters). The **device ID** is that hex string.

## 5. Pairing

### 5.1 Definitions

- The **pairing secret** is 32 random bytes generated by the Mac for each pairing window. It
  is **single-use** and **expires 5 minutes** after creation.
- **Secret proof:** `HMAC-SHA256(key = secret, msg = "anmirror-pair-v1" || mac_fp || phone_fp)`,
  where `||` is byte concatenation, the label is its ASCII bytes, and `mac_fp`, `phone_fp`
  are the 32 raw fingerprint bytes.
- **Confirmation code** (shown on both screens so the user can compare them):
  - `h = SHA-256("anmirror-sas-v1" || mac_fp || phone_fp)`
  - `code = uint32_be(h[0..4]) mod 1,000,000`, rendered as exactly 6 digits, **zero-padded**
    (for example `097702`). In vectors the code is therefore a JSON string.
- **Discovery key:** 32 random bytes generated once per Mac and sent to the phone in
  `PairComplete`. It is used for the rotating ID (section 6).

Vectors: `vectors/crypto.json` (`fingerprints`, `proofs`, `codes`). Fingerprints are computed
over the DER of the three committed test certificates (`protocol/testdata/identities`); each
entry has a `name` (`mac`, `phone`, `stranger`). The `codes` set includes a vector whose code
has a leading zero.

### 5.2 Pairing URI (QR code content)

```
anmirror://pair?v=1&fp=<b64url(mac_fp)>&s=<b64url(secret)>&h=<host>,<host>&p=<port>&n=<pct(mac_name)>
```

- `b64url` is RFC 4648 section 5 (URL-safe alphabet), **no padding**. Padding characters and
  the standard alphabet (`+`, `/`) are rejected.
- `pct` is RFC 3986 percent-encoding of the UTF-8 bytes; the unreserved characters
  (`A-Z a-z 0-9 - . _ ~`) are kept, everything else is `%XX` (uppercase hex).
- `h` is a comma-separated list of one or more hosts (IPv4 addresses or hostnames), in the
  order the phone should try them. Hosts MUST NOT contain `,` or `&`.
- `p` is the TCP port, `1..65535`. `n` is optional (empty name if absent).
- **Parsing:**
  - The URI MUST start with `anmirror://pair?`; otherwise `malformed`.
  - Unknown extra parameters are **ignored**.
  - A repeated parameter is `malformed`.
  - `v` missing or not a number is `malformed`; `v` other than 1 is `unsupportedVersion`.
    The version is checked before any other field, so a `v=2` URI is `unsupportedVersion`
    even if its other fields would not parse.
  - `fp` or `s` missing, not valid b64url, or not decoding to exactly 32 bytes: `malformed`.
  - `h` missing or containing an empty entry, `p` missing or out of range: `malformed`.
  - `n` that is not valid percent-encoding or not valid UTF-8: `malformed`.
- The phone tries the hosts in order, each with a 3 s connect timeout.

Vectors: `vectors/pairing_uri.json`. Each `valid` entry has the URI and the parsed `fields`
(`version`, `fp_hex`, `secret_hex`, `hosts`, `port`, `mac_name`); each `invalid` entry has the
URI and the expected error (`malformed` or `unsupportedVersion`). They include a name with a
curly apostrophe and an emoji (`Ada’s MacBook Pro \U0001F34E`) and two hosts.

### 5.3 Sequence

The phone scans the QR code, then connects as TLS client and **pins `fp` from the QR code** as
the Mac's identity. The Mac accepts the phone's (unknown) certificate only while a pairing
window is open.

1. Phone sends `pairing.request{protocol_version, secret_proof, device_name, device_model}`.
   If the protocol version is wrong, the Mac replies `system.error PROTOCOL_MISMATCH`.
2. The Mac computes the expected proof from its own fingerprint and the phone certificate's
   fingerprint, and compares in constant time.
   - Match: Mac sends `pairing.verified`.
   - Mismatch: `system.error BAD_PAIRING_SECRET`.
   - After **3** bad proofs, or when the secret has already been used, or is **5 minutes old**:
     `system.error PAIRING_EXPIRED`.
3. Both sides compute and show the **confirmation code**.
4. Each side sends `pairing.confirm{accepted}` when its user decides. `accepted = false` from
   either side means both show "Pairing cancelled" and the connection closes. Each side waits
   at most **60 s** for the user's decision.
5. When both sides have accepted, the Mac sends `pairing.complete{discovery_key, mac_name}`.
   Both sides persist the peer (device ID = fingerprint hex). The secret is now spent.
6. The phone then sends `system.hello` on the same connection.

`PAIRING_REJECTED` is sent when a side refuses to continue pairing for a reason other than a
user decline (for example the Mac's pairing window was closed).

### 5.4 Rules after pairing

- An **unpaired client certificate** is accepted only while a pairing window is open, and its
  first message MUST be `pairing.request`. Anything else gets `system.error NOT_PAIRED`, then
  the connection is closed.
- A **second paired phone** connecting while one is active gets `system.error BUSY`, then the
  connection is closed.
- Unpairing from either side sends `system.goodbye{UNPAIRED}`; a phone that moves to another
  Mac sends `SWITCHING_MAC`; an orderly quit sends `SHUTDOWN`.

## 6. Reconnection and rotating ID

A phone may find its Mac again by Bonjour without any personal data being advertised. The Mac
publishes TXT `r`, a rotating ID derived from the discovery key:

- `epoch = floor(unix_seconds / 900)` (15-minute epochs)
- `r = lowercase hex of HMAC-SHA256(key = discovery_key, msg = "anmirror-rid-v1" || uint64_be(epoch))[0..8]`
  (the first 8 bytes, so 16 hex characters)
- The phone accepts `epoch - 1`, `epoch` and `epoch + 1`, to tolerate clock skew.

Vectors: `vectors/crypto.json` `rotating_ids` (each entry also lists the `epoch`, and includes
values on both sides of an epoch boundary).

## 7. Keep-alive and lifecycle

Initial values (battery tuning is planned for 0.9):

- The phone sends `system.ping` every **30 s**. If no `system.pong` arrives within **10 s**,
  the phone drops the connection and reconnects.
- The Mac marks the phone as lost after **75 s** with no incoming message.
- On wake from sleep the Mac closes every connection and restarts its listener on the same port.

## 8. Errors

`system.error` carries an `ErrorCode` and a human-readable English `message` intended for logs,
not for display. Codes: `PROTOCOL_MISMATCH`, `NOT_PAIRED`, `BAD_PAIRING_SECRET`,
`PAIRING_EXPIRED`, `PAIRING_REJECTED`, `BUSY`. After `system.error` in the situations above the
sender closes the connection. Framing errors (section 2) close the connection without a reply.

## 9. Regenerating vectors and test identities

- `python3 -I protocol/tools/make_vectors.py` writes `protocol/vectors/*.json`;
  `... --check` regenerates in memory and exits 1 on any difference. The output is
  deterministic; the only external input is the committed test certificates.
- `scripts/make-test-identities.sh` creates the three test-only PKCS#12 identities (password
  `test`). **Re-running it creates new keys, which changes the fingerprints**, so the vectors
  must be regenerated and every implementation's tests re-run. The identities are for tests
  only and never ship in any app.
