# Milestone 0.2 (Notifications & Calls) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Phone notifications appear as native Mac notifications, with their actions, inline reply, dismissal sync both ways, per-app filtering and "Copy code". Phone contacts sync to a private, encrypted store on the Mac. Incoming calls show on the Mac with the caller's name, and can be answered, declined, muted and hung up from there. Missed calls show as notifications.

**Architecture:**
- **Protocol.** Three new channels and capabilities (`notify.v1`, `contacts.v1`, `calls.v1`), defined in `.proto` and SPEC.md like 0.1's features. No new crypto.
- **Phone.**
  - Decision logic lives in three Android library modules (`feature/notify`, `feature/contacts`, `feature/calls`). It is written against small interfaces, so it unit-tests on the JVM with fakes.
  - Android adapters implement those interfaces: the `NotificationListenerService`, `ContactsContract`, `TelephonyCallback`, `TelecomManager` and `AudioManager`.
  - `ConnectionService` wires them to the `ConnectionManager`, as 0.1 did for status and find.
- **Mac.**
  - Three SwiftPM targets in AMKit (`FeatureNotify`, `FeatureContacts`, `FeatureCalls`). Their logic is tested against fake presenters.
  - The app wires them to `MacServer`, `UNUserNotificationCenter`, the menu, Settings and an incoming-call panel.
- **No connection-core changes.** 0.2 adds channel enum cases and message types only. `ConnectionManager` and `MacServer` stay as reviewed in 0.1, because the screen-off keep-alive check (0.1 owner check (h)) may still rework them.

**Tech Stack:** as 0.1. New APIs:
- **Android:** `NotificationListenerService`, `RemoteInput`, `ContactsContract`, `TelephonyCallback` / `PhoneStateListener`, `TelecomManager`, `AudioManager`, `CallLog`.
- **Mac:** `UserNotifications`, `CryptoKit` AES-GCM, `NSPanel`.

No new third-party dependencies.

**Spec:** [docs/PRD.md](../../PRD.md) (F-03, F-06, F-09, F-14, §8), [docs/ARCHITECTURE.md](../../ARCHITECTURE.md) (§3.3, §4, §5, §7), [docs/ROADMAP.md](../../ROADMAP.md) §0.2. Protocol rules: [protocol/SPEC.md](../../../protocol/SPEC.md). This plan builds on branch `milestone-0.1`.

## Global Constraints

Everything in the 0.1 plan's Global Constraints still applies (platforms, licensing, privacy, TLS, identifiers, strings, accessibility). In addition:

**Privacy**
- **Never read SMS.** No `READ_SMS`, `RECEIVE_SMS`, `RECEIVE_MMS` or `READ_CELL_BROADCASTS` in any manifest. One-time codes come only from notification text that F-03 already passes to the Mac (PRD F-09).
- **The phone stores no notification content and no contacts at rest.** It reads them live and keeps them in memory only for the current session.
- **On the Mac:**
  - Notification content lives only in macOS Notification Center, plus an in-memory map for the session.
  - Contacts are stored **encrypted** (AES-GCM, with the key in the Keychain), one file per paired phone.
  - Turning contacts off wipes the store; forgetting the phone wipes it too (Architecture §7).
- **Each Android permission is requested only when its feature is turned on** from the phone app's home screen. Notification access goes through the Settings screen; contacts and phone permissions are runtime prompts.

**Play-ready switches** (Architecture §5)
- `BuildConfig.FEATURE_CALL_LOG` and `BuildConfig.FEATURE_ANSWER_CALLS` are both `true` in the `oss` flavor.
- With a switch off, the code must still compile and work:
  - **Number:** taken from the call notification (the dialer's notification title).
  - **Answer, decline and hang up:** done through the call notification's `CallStyle` intents.
  - **Missed calls:** found without the call log.
- Permissions guarded by a switch (`READ_CALL_LOG`, `ANSWER_PHONE_CALLS`) are declared in the `oss` flavor's manifest only (`android/app/src/oss/AndroidManifest.xml`).

**Wire limits** (a frame is at most 1,048,576 bytes, SPEC §2)
- Notification image: JPEG, long edge at most **720 px**, at most **300 KB**. If it doesn't fit after one re-encode at quality 60, it is dropped.
- App icon: PNG **96×96**, at most **32 KB**.
- Notification `title` at most **256 bytes**, `text` at most **4,096 bytes**, `sub_text` at most **256 bytes**, each cut at a UTF-8 character boundary, with "…" appended when cut.
- Contacts are sent in batches of at most **200 contacts**.

**Acceptance targets** (PRD, ROADMAP 0.2 exit)
- A notification reaches the Mac **within 1 s** on the same network.
- An inline reply sent from the Mac arrives in the phone app (WhatsApp).
- Dismissal syncs both ways.
- Answering and declining from the Mac works on Android 10–16. Only Android 16 is on hand, so other versions are recorded as untested.

**Copy (exact)**
- Mac:
  - `"Copy code"`
  - `"Missed call"`
  - `"Answer"`
  - `"Decline"`
  - `"Mute"` / `"Unmute"`
  - `"Hang up"`
  - `"This notification is no longer on the phone."`
  - `"Allow notifications for Android Mirroring in System Settings."`
  - `"Turn on notification access in the phone app."`
- Phone home rows:
  - `"Show notifications on your Mac"`
  - `"Calls on your Mac"`
  - `"Share contacts with your Mac"`

## Review Focus

These are the five failures a real person is most likely to hit that no feature test covers. Each one gets a test in the task named in brackets.

1. **An app updates the same notification over and over.** WhatsApp, for example, reuses one key per chat for each new message. Expected: the Mac replaces its notification instead of stacking copies. It alerts again only when the text changed, and never when the update was flagged "only alert once". *(Task 3 `repostWithSameContentDoesNotAlert`, `repostWithNewTextAlerts`, `onlyAlertOnceIsHonoured`; Task 4 `samePhoneKeyReplacesMacNotification`)*
2. **The user acts on a Mac notification that's already gone on the phone.** It was dismissed there, the app was updated, or its PendingIntent was cancelled. Expected: the phone answers `GONE`; the Mac removes the notification and shows "This notification is no longer on the phone." No crash, no silent loss. *(Task 3 `invokeOnMissingKeyReturnsGone`, `cancelledPendingIntentReturnsGone`; Task 4 `goneResultRemovesAndExplains`)*
3. **Notifications change while disconnected.** Expected: on reconnect the phone sends the list of active keys. The Mac removes any it shows that are no longer active, and shows the still-active ones it never received. *(Task 3 `connectSendsUndeliveredThenSnapshot`; Task 4 `snapshotRemovesStale`)*
4. **Odd content:** a 50 KB message, emoji, right-to-left text, no title, a 12 MP picture, or a notification with eight actions. Expected: text is cut at a character boundary with "…", and an oversized picture is dropped. Actions are capped at **3** (the Mac's practical limit, builder's call), with a reply action kept first. Nothing is ever sent over 1 MiB. *(Task 3 `truncatesAtUtf8Boundary`, `dropsOversizedImage`, `capsActionsKeepingReply`)*
5. **A call ends before the Mac user clicks, or a second call arrives during a call.** Expected:
   - Answering a call that has ended returns `NO_SUCH_CALL`, and the panel closes.
   - A second call ringing during an active one shows its own panel. That panel's Answer is offered only if the phone reports `can_answer`, which it does only for the first call (builder's call: no call-waiting swap in 0.2).
   
   *(Task 7 `commandOnEndedCallReturnsNoSuchCall`, `secondRingingDuringActiveIsReported`; Task 8 `endedCallClosesPanel`)*

**Rules** (builder's call; English only at launch):
- A code is one of:
  - 4–8 digits
  - two digit groups of 3–4 joined by one space or `-` (`"123 456"`, `"123-456"`)
  - `G-` followed by 6 digits (Google; returned without `G-`)
- It needs a keyword within the same notification, matched case-insensitively on title + text: `code`, `otp`, `verification`, `verify`, `passcode`, `password`, `pin`, `one-time`, `one time`, `2fa`, `security code`, `login`, `log in`, `sign in`, `authentication`.
- It is never part of:
  - a longer digit run
  - an amount, with a currency marker (`$ € £ ₹ Rs INR USD EUR`) within 2 characters before it
  - a time (`12:30`)
  - a date (`2026-10-28`, `28/10`)
- With several candidates, the one nearest a keyword wins. Ties go to the first.

```kotlin
data class ActionSnapshot(val title: String, val isReply: Boolean, val replyHint: String?)
data class NotificationSnapshot(
    val key: String, val packageName: String, val appName: String, val title: String, val text: String,
    val subText: String, val postedAtMs: Long, val actions: List<ActionSnapshot>,
    val ongoing: Boolean, val groupSummary: Boolean, val foregroundService: Boolean,
    val mediaStyle: Boolean, val category: String?, val onlyAlertOnce: Boolean, val clearable: Boolean,
)
object NotificationMapper {
    fun eligible(n: NotificationSnapshot, ownPackage: String, filter: NotificationFilter): Boolean
    fun toProto(n: NotificationSnapshot, imageJpeg: ByteArray?, alert: Boolean): PhoneNotification
    fun truncateUtf8(s: String, maxBytes: Int): String
}
interface ActionInvoker {
    fun invoke(key: String, actionIndex: Int, replyText: String?): ActionOutcome   // index into the capped list sent to the Mac
    fun dismiss(key: String)
    fun active(): List<NotificationSnapshot>
    fun image(key: String): ByteArray?     // already scaled by ImageScaler, or null
    fun icon(packageName: String): ByteArray?  // 96×96 PNG, or null
}
class NotifyBridge(
    private val ownPackage: String,
    private val invoker: ActionInvoker,
    private val send: suspend (type: String, payload: MessageLite) -> Boolean,
) {
    suspend fun onPosted(n: NotificationSnapshot)
    suspend fun onRemoved(key: String)
    suspend fun onConnected()                       // undelivered active ones, then notify.snapshot
    fun onDisconnected()
    suspend fun onFilter(f: NotificationFilter)
    suspend fun onInvoke(envelopeId: Long, a: InvokeAction): ActionResult
    fun onDismiss(d: DismissNotification)
    suspend fun onIconRequest(r: IconRequest)
}
```

**Rules:**
- **Eligible:**
  - not this app's own package
  - not `ongoing`, `groupSummary`, `foregroundService` or `mediaStyle`
  - not `category == "call"` (F-06 owns calls)
  - `filter.enabled`, and the package is not in `muted_packages`
  - Before any `notify.filter` has arrived this session, the filter is treated as `enabled = true` with nothing muted.
- **Mapping:**
  - Title and text come from `EXTRA_TITLE` and `EXTRA_BIG_TEXT ?: EXTRA_TEXT`.
  - For a `MessagingStyle` notification: the title is the conversation title, else the last message's sender, and the text is the last message.
- **Actions:**
  - The reply action comes first, then the others, in order, capped at 3.
  - `actionIndex` in `InvokeAction` refers to this capped order.
- **Alerting:**
  - `alert` is false when `onlyAlertOnce` is set and the key was already sent this session.
  - It is also false when the title + text equal what was last sent for that key.
- **Invoking:**
  - `invoke` returns `GONE` when the key is no longer active, or when `PendingIntent.send` throws `CanceledException`.
  - A reply uses `RemoteInput.addResultsToIntent` on the action's `RemoteInput`.
- **Dismissing:** `dismiss` calls `cancelNotification(key)` only for clearable notifications. It does not echo the removal back as a separate message; the listener's `onNotificationRemoved` sends `notify.removed` once.
- **Delivered set:** kept in memory for the current process. `onConnected` sends active, eligible keys not yet in it, then `notify.snapshot` with all active eligible keys.

**Rules:**
- **Phases:**
