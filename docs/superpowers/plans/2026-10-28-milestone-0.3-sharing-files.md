# Milestone 0.3 (Sharing & Files) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Files move both ways between the Mac and the phone (drop zone, menu, Android share sheet, Mac Share menu), with progress and cancel on both sides and 1 GB at ≥ 20 MB/s. Text copied on the Mac is on the phone automatically; phone text reaches the Mac from a Quick Settings tile, a notification action or the share sheet. Links open in the other device's browser. Phone screenshots land on the Mac within seconds. A Mac window shows the newest 200 photos and lets the user browse, download, upload, rename and delete phone files; in the Full build the phone also appears in Finder's sidebar.

**Architecture:**
- **Protocol.** Six new channels and capabilities (`clipboard.v1`, `share.v1`, `files.v1`, `screenshots.v1`, `photos.v1`, `browse.v1`), in `.proto` and SPEC.md §13–§19 like 0.2's features. Small messages stay on the control connection; file bytes and thumbnails go over **bulk connections** (Architecture §3.3): a second TLS listener on the Mac, same pinning, one connection per transfer, opened by the phone with a single-use token.
- **One transfer engine per side.**
  - **Phone:** a pure-JVM module `core/transfer`, so `phone-sim` runs the same code as the app.
  - **Mac:** the AMKit target `FeatureFiles`.
  - Every feature that moves bytes uses the engine: share, screenshots, photo downloads and browse reads and writes.
- **Phone.**
  - Decision logic lives in JVM-testable modules: `feature/clipboard`, `feature/share`, `feature/screenshots`, `feature/photos`, `feature/browse`.
  - Android adapters live beside them or in `app/platform`: MediaStore, Storage Access Framework, `ClipboardManager`, `TileService`.
  - `ConnectionService` and `AppGraph` wire everything with 0.2's gating pattern.
- **Mac.**
  - AMKit targets `FeatureFiles`, `FeatureClipboard`, `FeatureShare`, `FeatureScreenshots`, `FeaturePhotos`, `FeatureBrowse` and `FileProviderShared`.
  - Each feature model conforms to a new `SessionFeature` protocol, and `NotifyWorkQueue` routes the new channels through its single ordered queue.
  - The app adds a "Phone" device window (Send / Photos / Files tabs), menu items and Settings.
  - A separate **Full** project spec adds the Share and File Provider extensions; the default **Contributor** project has none.
- **No connection-core logic changes.** `ConnectionManager`, `PhoneSession`, `MacServer` and `ControlConnection` stay as reviewed. Bulk transport is new files (`BulkServer`, `BulkConnector`). `TlsConnector` gains one added internal function and is otherwise unchanged.

**Tech Stack:** as 0.2. New APIs:
- **Android:** `MediaStore` (Downloads, Images, Files, `loadThumbnail`), the Storage Access Framework (`ACTION_OPEN_DOCUMENT_TREE`, `DocumentsContract`), `ClipboardManager`, `TileService`, `ContentObserver`, `java.nio.file`.
- **Mac:** `Network.framework` (`NWListener`), `CryptoKit` SHA-256, `NSPasteboard`, `NSWorkspace`, `NSItemProvider` file representations, `NSFileProviderReplicatedExtension`, Share extension (`NSExtensionPointIdentifier com.apple.share-services`), `NSXPCConnection`.

No new third-party dependencies.

**Spec:** [docs/PRD.md](../../PRD.md) (F-04, F-05, F-10, F-12, F-13, §8, §9, §11), [docs/ARCHITECTURE.md](../../ARCHITECTURE.md) (§3.3, §4, §5, §7), [docs/ROADMAP.md](../../ROADMAP.md) §0.3. Protocol rules: [protocol/SPEC.md](../../../protocol/SPEC.md). This plan builds on branch `milestone-0.3` (0.1 and 0.2 complete, from `02283a6`).

## Global Constraints

Everything in the 0.1 and 0.2 plans' Global Constraints still applies (platforms, licensing, TLS, identifiers, strings, accessibility, gating). In addition:

**Hard rules carried from 0.1 and 0.2**
- **Leave the reviewed connection code alone.** No logic changes to `ConnectionManager`, `PhoneSession`, `MacServer` or `ControlConnection` (0.1 owner check (h) may still rework keep-alive). New transport goes in new files. Adding channel enum cases and message types is fine.
- **Phone gating:** the phone sends no feature message unless all three hold: the Mac shares the capability, the user's switch is on, and the permission is granted. The only exception is `<feature>.availability`. Use `featureAvailability(granted, userOn)`.
- **Mac routing:** every phone message reaches its model through the single ordered `NotifyWorkQueue` (Task 4 adds `SessionFeature`). Bulk bytes do not go through the queue; they are data, not messages.
- **Never read SMS.** The 0.2 manifest audit still holds.
- **No content in logs on either side:** no clipboard text, file names, browse paths, file bytes, thumbnails or photo metadata. Log only transfer IDs, sizes, durations, MB/s and error codes.
- **Each Android permission is requested only when its feature is turned on** from the home screen.

**Privacy and storage**
- Thumbnails live **in memory only** on the Mac. They are cleared on disconnect and when the Phone window closes (Architecture §7).
- Partial files are removed on every failure path:
  - **Mac:** a hidden `.<uuid>.part` in the destination folder.
  - **Phone:** the MediaStore row with `IS_PENDING = 1`, or a `.<uuid>.part` in a browse root.
- The phone keeps nothing from the Mac except files the user received.

**Play-ready switches** (Architecture §5)
- `BuildConfig.FEATURE_ALL_FILES` is `true` in `oss`; `-PplayLike=true` sets it to `false`, alongside 0.2's two switches.
- `MANAGE_EXTERNAL_STORAGE` is declared in `android/app/src/oss/AndroidManifest.xml` only.
- With the switch off, or on Android 10 (builder's call: All files access is offered on API 30+ only), browsing uses picked folders.

**Wire and bulk limits**
- A frame is at most 1,048,576 bytes (SPEC §2).
- **Text:**
  - `ClipboardText.text` and `SharedText.text`: at most **262,144 bytes UTF-8** (builder's cap). Larger text is not sent, and the sending side says so.
  - `SharedLink.url`: at most 8,192 bytes, `http` or `https` with a host. Anything else is sent as text.
- **File names:** at most 255 bytes UTF-8 after sanitizing (SPEC §16, `vectors/filenames.json`).
- **Pages:**
  - `browse.listing`: at most **500** entries per page.
  - `photos.items`: at most **200**.
  - `photos.thumbs`: at most **200** IDs.
- **Thumbnails:** JPEG, long edge **256 px**, quality 80, re-encoded once at 60 if over **64 KB**, otherwise sent empty (length 0).
- **Bulk connections:**
  - **256 KiB** read/write buffers; file I/O off the network thread and off the main actor; no protobuf per chunk; SHA-256 computed while streaming.
  - Token: 32 random bytes, single use, expires after **60 s**.
  - The `bulk.hello` must arrive within **10 s**.
  - A transfer with no bytes moved for **30 s** fails `TIMED_OUT`.
  - The sender waits **30 s** for `files.accept`.
  - The receiver reports progress at most every **500 ms**.
- **Free space:** an offer is rejected `NO_SPACE` when `size + 64 MiB` exceeds the destination's free space.

**Acceptance targets** (PRD, ROADMAP 0.3 exit)
- **Files:** 1 GB at ≥ 20 MB/s on 5 GHz Wi-Fi, both directions. An interrupted transfer reports failure clearly on both sides.
- **Finder browsing** works with All files access and with picked folders. The in-app Files tab is the fallback where the File Provider can't run.
- **Photos:** the newest 200 photos and videos load as thumbnails in under 3 s.
- **Clipboard:** text pastes on the other side within 1 s of the copy or trigger.

## Review Focus

These are the five failures a real person is most likely to hit that no feature test covers. Each one gets a test in the task named in brackets.

1. **Hostile or odd file names:** `../../etc/passwd`, `a/b.txt`, `..\x.exe`, `.hidden`, `....`, control characters, a right-to-left override, emoji, a 300-byte name, or a second `photo.jpg`. Expected: both sides produce the same safe name (path stripped, never empty, ≤ 255 bytes, extension kept), and a collision becomes `photo (1).jpg`. Nothing is ever written outside the destination folder. *(Task 1 `filenames.json`; Task 3 `sanitizeMatchesVectors`, `uniqueAddsCounterWithinCap`; Task 4 `sanitizeMatchesVectors`, `collisionGetsCounter`)*
2. **The Mac sleeps, Wi-Fi drops or the app quits mid-transfer.** Expected:
   - Both sides show "Couldn't … The connection was lost."
   - The partial file is gone.
   - No bulk connection is left open, and outstanding tokens stop working.
   - The queue moves on after reconnecting; nothing resumes (ROADMAP 1.x).

   *(Task 2 `revokeAllRejectsOutstandingTokens`; Task 3 `disconnectFailsActiveAndAbortsPartial`, `bulkEndsEarlyFailsInterrupted`; Task 4 `disconnectFailsAndDeletesPartial`, `stalledLinkTimesOut`)*
3. **Clipboard echo and password managers.** Expected:
   - A password copied from a password manager (`org.nspasteboard.ConcealedType`, `TransientType`, `AutoGeneratedType`) is never sent.
   - Text that came from the phone, by clipboard or by share, is not sent back when the Mac's change counter moves.
   - The phone doesn't bounce the Mac's text back either.

   *(Task 5 `concealedTypeIsNotSent`, `transientAndAutoGeneratedAreNotSent`, `textFromPhoneIsNotEchoed`, `macTextIsNotSentBack`; Task 7 `sharedTextFromPhoneIsNotEchoed`)*
4. **Low disk space on the receiving side.** Expected: the receiver rejects with `NO_SPACE` before any byte moves. The sender shows "Not enough space on the Mac/phone." and moves on to the next queued file. *(Task 3 `offerLargerThanFreeSpaceIsRejected`; Task 4 `offerLargerThanFreeSpaceIsRejected`, `rejectShowsReasonAndStartsNext`)*
5. **Fifty files shared at once, or a 5 GB video.** Expected: the files queue and run one at a time per direction, with one bulk connection at a time and each file finishing or failing on its own. Sizes above 4 GiB keep their full 64-bit value in offers, progress and hashing. *(Task 3 `fiftyFilesRunOneAtATime`, `sizeAbove4GiBIsKept`; Task 4 `fiftyFilesRunOneAtATime`, `sizeAbove4GiBIsKept`)*

- [ ] **Step 1: Write the SPEC changes first.**
  - Add the rows to §3 and the six capability strings to "Capabilities".
  - Add the sections below. Renumber nothing.
  - **Mac-originated requests carry their own `request_id`** (a Mac counter echoed by the phone), not envelope `reply_to`. This is a builder's call: `MacServer.send` does not expose envelope IDs and must not change.
  - **§13 Bulk connections:**
    - The Mac runs a second TLS 1.3 listener on an ephemeral port, with the same pinning as §1. It accepts only the connected, paired phone's certificate.
    - It announces the port with `files.endpoint` right after connect, whenever any of `files.v1`, `screenshots.v1`, `photos.v1` or `browse.v1` is shared.
    - The phone always dials. Its first frame is a normal §2 frame whose envelope is `{channel FILES, id 1, type "bulk.hello"}` carrying `BulkHello`.
    - Tokens are issued by the Mac only: in `files.offer` when the Mac sends, in `files.accept` when the Mac receives, and in `photos.thumbs`. A token is 32 random bytes, single-use and expires after 60 s.
    - An unknown, expired or reused token, or a role that doesn't match the token, closes the connection without a reply.
    - After the hello, the sender writes exactly `size` raw bytes. The receiver reads exactly `size` bytes and never waits for EOF; extra bytes fail the transfer. The sender closes after `files.received` / `files.failed`, or after 30 s.
    - A control disconnect revokes every token and ends every bulk connection.
  - **§14 Clipboard:** plain text, at most 262,144 bytes, both directions. Concealed, transient and auto-generated pasteboard items are never sent. Neither side sends back text whose SHA-256 equals the last text it received from the peer.
  - **§15 Share:**
    - `share.link` is only `http`/`https` with a host, at most 8,192 bytes; anything else is sent as `share.text`.
    - The receiver opens the link (on the phone, after a tap on a notification).
    - `share.text` lands on the clipboard with a notification.
    - Files are §16 transfers.
  - **§16 Files.** The sequence is as in this plan's Task 3 and Task 4 rules:
    - **The steps:** offer, then accept or reject, then the bulk bytes. During the bytes the receiver sends progress (at most every 500 ms) and the sender sends `files.complete` with the SHA-256. The receiver then answers with `files.received`, or `files.failed HASH_MISMATCH`.
    - **Cancel:** either side may cancel, and no reply is sent.
    - **Queueing:** one transfer at a time per direction; the next offer waits until the previous transfer ended.
    - **Auto-accept:** offers from the paired peer are accepted automatically. This is a builder's call: both are the user's own devices.
    - **Free space:** an offer is rejected `NO_SPACE` when `size + 64 MiB` exceeds free space.
    - **No resume.**
    - **The file-name rule:**
      1. Take the text after the last `/` or `\`.
      2. Remove C0 controls, DEL and the bidi controls U+202A–U+202E and U+2066–U+2069.
      3. Strip leading dots and spaces and trailing spaces.
      4. If nothing is left, use `file`.
      5. Cap at 255 bytes UTF-8, cutting the stem at a Unicode scalar boundary and keeping an extension of at most 16 bytes.
      6. On a collision, use `stem (n).ext` with the smallest free `n ≥ 1`, still within the 255-byte cap.
  - **§17 Screenshots:** the phone sends `TRANSFER_KIND_SCREENSHOT` offers. `screenshots.availability` may say `PARTIAL_ACCESS`, which means new screenshots can't be found.
  - **§18 Photos:**
    - `photos.list` (limit 1–200) is answered by `photos.items`, newest first.
    - `photos.thumbs` is answered over one bulk connection with role `THUMBNAILS`. Each record is `uint64_be id | uint32_be length | JPEG`, in request order; length 0 means no thumbnail, and a length over 1 MiB is an error. The stream ends with the record `id = 0, length = 0`.
    - `photos.fetch` is answered by a `TRANSFER_KIND_PHOTO` offer with its `request_id`, or by `files.failed{request_id, NOT_FOUND}`.
    - `PARTIAL_ACCESS` means the list holds only the items the user picked.
  - **§19 Browse:**
    - **Paths** are relative to a root and `/`-separated; `""` is the root itself. A segment that is empty, `.` or `..`, or contains `\0`, and any path with a leading `/` or a path over 4,096 bytes, is `BAD_PATH`. Symlinks that resolve outside the root are neither listed nor followed.
    - **Listing:** `browse.list` pages are sorted directories first, then by name (case-insensitive), with `limit` clamped to 1–500.
    - **Deleting** is recursive, and never follows symlinks.
    - **Renaming:** `new_name` must equal its own sanitized form, else `BAD_PATH`.
    - **Reading:** `browse.read` is answered by a `TRANSFER_KIND_FILE` offer with `request_id`, or by `browse.result` with the failure.
    - **Writing:** a write is a Mac `files.offer` with `target`. With `overwrite = false` a collision gets the §16 counter.
    - **Revoked folders:** a picked folder whose permission was revoked answers `REVOKED`, and the phone pushes an updated `browse.roots`.

**Rules:**
- **Phone sends:**
  1. `files.offer` (without a token), then wait up to `acceptTimeoutMs`.
  2. On `files.accept`, open the bulk stream with `BulkHello{token, PHONE_SENDS}`.
  3. Copy exactly `size` bytes in 256 KiB chunks on `io`, hashing as it goes.
  4. Send `files.complete{sha256}`, then wait for `files.received` → DONE, or `files.failed` → FAILED.
  5. Close the stream.
- **Phone receives:**
  1. On `files.offer`, check free space and run `sinks.open`. A refusal sends `files.reject{reason}`.
  2. Otherwise send `files.accept{transfer_id}`, then open the bulk stream with `BulkHello{offer.token, PHONE_RECEIVES}`.
  3. Read exactly `size` bytes into the sink while hashing, sending `files.progress` at most every `progressIntervalMs`.
  4. When the bytes are in and `files.complete` has arrived (in either order), compare the hashes. On a match, `commit()` and send `files.received`; on a mismatch, `abort()` and send `files.failed HASH_MISMATCH`.
- **Failures:**
  - EOF before `size` → `INTERRUPTED`.
  - No bytes for `stallTimeoutMs` → `TIMED_OUT`.
  - Each sends `files.failed` and aborts the sink.
  - `cancel` sends `files.cancel`, and an incoming `files.cancel` stops the transfer. Both close the stream and abort.
- **Queueing:** one SEND and one RECEIVE may run at once; further sends wait in order.
- **`onDisconnected`:** every non-final transfer becomes `FAILED INTERRUPTED`, its stream is closed, and its sink is aborted. Nothing is sent.
- **Logging:** IDs, sizes, durations and error codes only.

  - Writes go to `.<uuid>.part` and are renamed on `commit()`. With `overwrite` they replace the old file; without it they get `FileNames.unique`.
- **`SafFileTree`:**
  - It resolves each segment by querying the children with `DocumentsContract.buildChildDocumentsUriUsingTree` and caches path → document ID for the session.
  - A `SecurityException` returns `REVOKED`; `BrowseService` then drops that root (`PickedFolders.remove`) and calls `pushRoots()`.
- **`BrowseService`:**
  - Sorts directories first, then by name (case-insensitive), and pages with the limit clamped to 1–500.
  - `rename` refuses a `new_name` that differs from `FileNames.sanitize(new_name)` (`BAD_PATH`).
  - `onRead` sends `transfers.send(listOf(file), FILE, requestId)` or `browse.result{failure}`.
  - Every answer echoes `request_id`.
- **Home row "Browse phone files from your Mac":** a switch, default off.
  - When on:
    - with `FEATURE_ALL_FILES` on API 30+, an "Allow access to all files" button (`Settings.ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION` with `package:` URI) until access is granted
    - always an "Add folder" button (`ACTION_OPEN_DOCUMENT_TREE`, then `takePersistableUriPermission` read+write)
    - the picked folders, each with "Remove", which calls `releasePersistableUriPermission`
  - `browse.availability`: `featureAvailability(granted = roots non-empty, userOn)`.
