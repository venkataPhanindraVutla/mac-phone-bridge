# F-20 Phone as Mac webcam: research

Status: **Research** · Date: 2026-11-14 · Related: [PRD §7](../PRD.md#7-version-2-features-later) · [Architecture](../ARCHITECTURE.md) · [Roadmap](../ROADMAP.md) · [F-21 mic report](2026-11-14-f21-microphone.md)

**Goal:** the phone's camera appears as a camera in FaceTime, Zoom, Meet, Photo Booth and every other Mac app.

**Short answer:** on macOS 14+, the **only** supported way to add a camera that every app can see is a **Core Media I/O Camera Extension**, and that is a **system extension**. A free Apple ID **cannot** sign one, and installing one on a normal Mac needs a **notarized** build. Both need the paid Apple Developer Program (or the nonprofit fee waiver). The `systemextensionsctl developer` route doesn't help, because skipping notarization needs **SIP disabled**, which the user has ruled out. **F-20 is blocked until there is a paid account.** The phone side and the video pipeline mostly exist already.

Legend: ✅ checked against a primary source · ⚠️ partly checked · ❓ not verified

## 1. Mac side: Camera Extension requirements

From Apple's "Creating a camera extension with Core Media I/O" ✅ [1]:
- Camera extensions are a type of **system extension** (macOS 12.3+). They live inside the app bundle and the app activates them with `OSSystemExtensionRequest.activationRequest`.
- The app target needs two capabilities: **System Extension** and **App Groups**. The extension's `CMIOExtensionMachServiceName` must use that app group.
- **Only apps in `/Applications` can activate** an extension.
- **An admin user must approve it** in System Settings before apps can use it.

From Apple's "Installing System Extensions and Drivers" ✅ [2], activation checks:
- the extension's code signature
- that its **entitlements match those granted to your development team**
- that the app is in an Applications folder.

From Apple's "Debugging and testing system extensions" ✅ [3]: "Xcode doesn't notarize apps or system extensions during the normal development cycle, so **disabling SIP bypasses the notarization checks** that the system normally performs." In other words, a normal SIP-on Mac requires a **notarized** system extension. Notarization needs a Developer ID, which is a paid-program feature.

### Can a free Apple ID do it? No. ✅

Apple's **"Supported capabilities (macOS)"** table [4] (read 2026-11-14):

| Capability | ADP (paid) | Developer ID (paid) | Apple Developer (free) |
|---|---|---|---|
| System Extension | ✓ | ✓ | **—** |
| App Groups | ✓ | ✓ | ✓ |

The `com.apple.developer.system-extension.install` entitlement comes only from the System Extension capability ✅ [5]. Apple's forums show Xcode saying "Personal development teams … do not support the System Extension capability", and Apple DTS says the free column is everything free provisioning gets ⚠️ [6] (forum posts, consistent with the table).

### What `systemextensionsctl developer on` would demand

- ✅ Per the local man page and Apple's doc [3], developer mode **only skips the location check** (load from outside `/Applications`) and the version check. It does **not** skip signing, entitlement or notarization checks.
- ✅ Skipping notarization needs **SIP disabled** [3]. That needs Recovery mode and changes Mac security. The user has said no, and we can't ask end users to do it either.
- ❓ Even with SIP off, a free account still can't produce the entitlement. Some developers report AMFI tricks on top, but those go further into "change Mac security" territory. Not considered.

**Conclusion: no legal, SIP-on, free-account path to a real system camera exists.**

## 2. Alternatives without a paid account

| Path | Works? | Notes |
|---|---|---|
| Legacy DAL plug-in (`/Library/CoreMediaIO/Plug-Ins/DAL`) | ✅ **No** | macOS 14.1+ no longer loads DAL plug-ins [7]. Apple's own apps never loaded them [8]. |
| Continuity Camera | No | iPhone only. |
| **OBS Studio's Virtual Camera** (free, signed and notarized by OBS) | ⚠️ Yes, clunky | The user adds our mirror or camera window to OBS as a "Window Capture" source and starts OBS's virtual camera. No code for us; just a guide page. Not "native" (PRD §2), but honest and legal. OBS is GPL-2.0, so we only document it and copy nothing. |
| **"Phone camera" window** in our app (Full mode) | ✅ Yes | The vendored scrcpy helper already has `CameraCapture` (`--video-source=camera`, **Android 12+**) [9]. It is a mirror session with a different source. Users can share that window in Zoom or Meet ("share a window"), or capture it with OBS. About 1 week of work. |
| Pay $99/year or get the nonprofit fee waiver | ✅ | The real fix. Unblocks F-20, notarization, the Finder/Share extensions and the Homebrew cask together. |

## 3. Android side

### Full mode (Android 12+): mostly free

- The helper's `CameraCapture.java` (vendored scrcpy v5.0.1) opens Camera2 and feeds the hardware encoder. It supports camera choice (front/back/id), size, fps and aspect ratio ✅ [9].
- The shell user holds **`CAMERA`** and **`BACKGROUND_CAMERA`** in AOSP ✅ [10]. So the helper can stream with the phone locked or the screen off, which is good for a phone on a stand. ❓ Some phone makers may still stop the camera when the screen turns off; test on the matrix.
- scrcpy documents Linux webcam use (camera → V4L2 loopback). That is the same idea we need, with a Camera Extension instead of V4L2 ✅ [9].
- Spec work: pass `video_source=camera`, `camera_facing`, `camera_size` and `camera_fps` in `mirror.start` (SPEC §24 lists the options passed today).

### Basic mode (no developer mode): possible, with one phone tap

- **CameraX or Camera2** with the encoder's input `Surface` as the target. Encode with `MediaCodec` H.264 at about 720p30 or 1080p30.
- Foreground service type **`camera`** + `FOREGROUND_SERVICE_CAMERA` (normal permission ✅ [11]) + runtime `CAMERA`.
- ✅ **While-in-use rule:** like the mic, a camera foreground service can't be started from the background. A notification tap or a tile tap is an allowed start [12]. So "Start phone camera" needs one tap on the phone.
- ⚠️ Android 12+ shows the green camera dot; the phone screen can usually be off while a camera foreground service runs, but that is maker-dependent.

## 4. Encoder, pipeline and latency

**Pipeline:** phone camera → H.264 hardware encoder → bulk TLS connection (a new role, or `MIRROR_VIDEO`) → Mac `VTDecompressionSession` (already in `FeatureMirror`) → `CVPixelBuffer` → our app sends frames to the Camera Extension's **sink stream** → the extension's **source stream** → Zoom etc.

- Apple's WWDC22 session 10022 covers sink streams, where an app feeds frames into its own extension ⚠️ [13] (from memory of the session; video not re-watched for this report). OBS's macOS virtual camera does the same; don't copy it (GPL).
- **Encoder:** H.264 for compatibility, H.265 when both sides support it (as in mirroring). Request low latency (`KEY_LOW_LATENCY`, Android 11+), short GOP, keyframe on request. About 4 Mbit/s for 720p30 and 6–8 Mbit/s for 1080p30.
- **Format to apps:** expose 1280×720 and 1920×1080 at 30 fps, `420v`. Apps ask for what they want.

**Latency estimate (glass to app, one way):**

| Step | Estimate |
|---|---|
| Sensor exposure + ISP | 30–50 ms ❓ |
| Encode | 10–20 ms ⚠️ |
| Wi-Fi + TLS | 5–20 ms ❓ |
| Decode | 5–10 ms ⚠️ |
| Extension queue (one frame) | ~33 ms |
| **Total** | **~85–130 ms** |

That is fine for video calls. Use the phone mic too (F-21) to keep lip sync. Mixing the phone camera with the Mac's own mic puts audio about 100 ms ahead of video, which people notice more than late audio. The Mac app could add a "delay Mac mic" option later.

## 5. What it means for the roadmap

- F-20 has a **hard dependency on the paid account or nonprofit fee waiver**. Today that's listed under v1.x (ROADMAP "After the project becomes a nonprofit"). Make it explicit: **F-20 can't ship before that.**
- The same account also unblocks notarization (no more "Open Anyway"), the Finder and Share extensions, and the Homebrew cask. So the $99 has value well beyond F-20.
- Work that **can** happen now, without the account:
  1. Full-mode "Phone camera" window (reuses the helper's camera source), plus a guide for using it via screen share or OBS.
  2. The camera options in the protocol (`video_source` etc.) and the Basic-mode camera service on Android, so only the Mac extension is left.
- F-21 (mic) is **not** blocked the same way (a HAL plug-in is not a system extension). That supports the agreed order: mic → webcam → call audio.

## 6. Recommendation

**Build later: after the paid Apple account or fee waiver.** Optionally build the "Phone camera window" now as a small step.

- **Rough size:**
  - Camera Extension + sink feeding + activation and approval UX + Basic-mode Android camera service: about 4–6 weeks.
  - "Phone camera window" (Full mode) only: about 1 week.
- **Spike on day 1 once the account exists:** the Xcode camera-extension template, Developer ID-signed and notarized, activated from `/Applications` on macOS 14 and 26.

**What the user must decide:**
1. **Pay the $99/year now**, or wait for the nonprofit fee waiver? (F-20 can't start until one happens.)
2. Build the **"Phone camera window" (Full mode, Android 12+)** now as a stopgap, or skip it?
3. Basic mode too (one phone tap each time), or Full mode only at first?
