# F-23 Call audio on the Mac: research

Status: **Research** · Date: 2026-11-14 · Related: [PRD §6 F-06, §7](../PRD.md) · [Architecture §5–6](../ARCHITECTURE.md) · [F-21 mic report](2026-11-14-f21-microphone.md)

**Goal:** during a phone call, hear the caller through the Mac's speakers and talk through the Mac's mic.

**Short answer:**
- **Basic mode (a normal app): not possible.** Every Android API that reads or writes call audio is reserved for system apps.
- **Full mode (shell helper, uid 2000):**
  - **hearing** the caller may work on some phones
  - **talking** into a cellular call works only on phones whose audio hardware exposes a special "telephony TX/RX" path, which we can't count on
  - for **VoIP calls** (WhatsApp, Meet on the phone) there's a more promising Android 13+ path.
- **The closest honest alternative is Bluetooth:** the Mac acts as a hands-free "car kit" for the phone, which is how Microsoft Phone Link does calls on Windows. macOS still ships that API, but nobody has shown it working on current macOS. It needs a spike.

Legend: ✅ checked against a primary source · ⚠️ partly checked or depends on the device · ❓ not verified

---

## 1. What a normal app (Basic mode) can do

| Mechanism | What it gives | Third-party app? |
|---|---|---|
| `MediaRecorder.AudioSource.VOICE_CALL` / `VOICE_UPLINK` / `VOICE_DOWNLINK` | Record call audio | ✅ **No.** Needs `CAPTURE_AUDIO_OUTPUT`, protection level `signature\|privileged\|role` [1] |
| `AudioManager.getCallUplinkInjectionAudioTrack()` / `getCallDownlinkExtractionAudioRecord()` (Android 13) | Exactly this feature: inject into the uplink and read the downlink | ✅ **No.** `@SystemApi`, needs `CALL_AUDIO_INTERCEPTION` (`signature\|privileged\|role`) [1][2] |
| `CallStreamingService` (Android 14) | Stream a call to another device | ✅ **No.** `@SystemApi`, needs the `SYSTEM_CALL_STREAMING` role, which is static and filled by the phone maker's config [3][4] |
| `InCallService` (be the default dialer) | Call UI and control, and choosing a route (earpiece/speaker/Bluetooth/wired) | ⚠️ Yes, but **no audio streams**: the modem and audio HAL move call audio, and a dialer only picks among hardware routes. It also means replacing the user's phone app. |
| `ConnectionService` (self-managed) | For a VoIP app's **own** calls | Not for cellular calls. |
| Recording the mic during a call | — | ✅ **No.** "The call always receives audio", and ordinary apps get silence [5] |
| Accessibility + speakerphone tricks | Old call-recorder hack | Bad quality, against Play policy, and still can't *inject* the Mac mic. Not considered. |

**Basic mode can't do F-23. That isn't a missing feature; Android forbids it on purpose.**

## 2. What the Full-mode shell helper (uid 2000) can do

The shell user is not a normal app. AOSP's Shell manifest grants it, for CTS testing ✅ [6]:

| Permission | In Shell's manifest since | Comment in AOSP |
|---|---|---|
| `CAPTURE_AUDIO_OUTPUT` | Android 11 (in `android11-release` and every later branch) | "Permissions required for GTS test - GtsDialerAudioTestCases" |
| `MODIFY_AUDIO_ROUTING` | Android 13 | — |
| `CALL_AUDIO_INTERCEPTION` | Android 13 | "Permission required for CTS test - CallAudioInterceptionTest" |
| `MODIFY_PHONE_STATE`, `BLUETOOTH_PRIVILEGED` | (present on main) | testing |

(We checked the `android11-release` … `android16-release` branches of `packages/Shell/AndroidManifest.xml`.)

What that allows, in theory:

1. **Hearing the caller (downlink).** The vendored scrcpy helper already has `voice-call`, `voice-call-uplink` and `voice-call-downlink` sources ✅ [7] (`AudioSource.java`). One scrcpy user reports `voice-call-downlink` working on a OnePlus/Oppo phone (CPH2585) ⚠️ [8]. Many phones' audio hardware returns **silence** for these sources ❓, and scrcpy notes the source produces no packets outside a call, which upsets timing ✅ [9]. **It depends on the device, and we don't know about the owner's phones.**

2. **Talking into a cellular call (uplink).** This is the hard half.
   - Mic injection through an audio policy (shell, Android 13+) is what scrcpy's open PR "Forward client audio" does ✅ [8]. It reaches **apps that record the mic**, but a tester found that during a cellular call **the other person did not hear the computer's mic** ✅ [8]. The modem takes the mic below Android's audio policy.
   - The proper API is `getCallUplinkInjectionAudioTrack()`. For a cellular (PSTN) call it throws unless `isPstnCallAudioInterceptable()` is true. That is true **only if the device lists both a `TELEPHONY_TX` output and a `TELEPHONY_RX` input** ✅ (AOSP `AudioService.java` [2]). Some Pixel device trees add "incall playback and capture" paths ⚠️ [10], but there's no public list of phones, and Samsung or Xiaomi support is ❓.
   - So: **two-way cellular call audio via the helper = maybe on some phones, never as a promise.**

3. **VoIP calls on the phone (WhatsApp, Signal, Meet).** ⚠️ More promising. In `AudioManager`, the injection and extraction calls also work when the audio mode is `MODE_IN_COMMUNICATION` (`CALL_REDIRECT_VOIP`). In that case AOSP builds them on a dynamic audio policy instead of the telephony hardware ports ✅ [2]. A shell helper with `CALL_AUDIO_INTERCEPTION` on Android 13+ could therefore move a WhatsApp call's audio to the Mac on **any** phone. ❓ Untested; calling these hidden `@SystemApi` methods from the helper needs reflection, as scrcpy already does elsewhere. (For VoIP the user could also just use WhatsApp/Meet on the Mac.)

Limits that apply to all of this: Full mode only (Android 11+, Wireless debugging on), it breaks if Wireless debugging drops mid-call, and it relies on test-only permissions that Google could remove from Shell in any release.

## 3. Bluetooth hands-free: the honest alternative

On a phone call, Android already knows how to send audio to a **Bluetooth hands-free device** (car kit, headset) using the standard HFP profile. The phone is the "Audio Gateway"; the device is "Hands-Free". No special Android permission is needed: the user pairs once and the phone routes the call audio. This works in **Basic mode on every phone**, with no developer mode.

- ✅ Microsoft Phone Link on Windows makes and takes Android calls this way. Microsoft says calls need Bluetooth on both PC and phone and a separate Bluetooth pairing [11].
- ✅ macOS still ships the API: `IOBluetoothHandsFreeDevice` ("manage phone calls on a connected Bluetooth hands-free phone"). It has `connectSCO`, `transferAudioToComputer` and `transferAudioToPhone` (IOBluetooth headers in the current macOS 27 SDK, **not deprecated**; available since macOS 10.7) [12].
- ❓ **Not verified that it still works on macOS 14–26.** Old Mac apps used it (e.g. Phone Amego), but we found no recent report of it working with a modern Android phone. We also don't know whether the SCO audio shows up as a Core Audio device and whether the Mac advertises the Hands-Free profile to the phone. **This is the key unknown.**
- Quality: HFP is "phone quality". Narrowband CVSD is 8 kHz; wideband mSBC is 16 kHz, if both sides support it. That's fine for calls.
- Our app would add the call UI (F-06 already has it), plus "Use Mac for call audio" that calls `transferAudioToComputer`.
- Downsides: a second pairing (Bluetooth, besides our Wi-Fi link), and range is Bluetooth range.

## 4. Phone-maker differences

- ⚠️ Whether `VOICE_CALL`/`VOICE_DOWNLINK` returns real audio, and whether `TELEPHONY_TX/RX` exist, depends on each maker's audio HAL. Expect it to differ even between models of the same brand.
- Samsung and Xiaomi ship their own system call recorders (system apps), which says nothing about what *we* can do.
- Bluetooth HFP is a standard every phone supports. Maker differences there are small: codec support (mSBC), and some battery savers dropping the Bluetooth link.

## 5. Recommendation

**Don't build F-23 as a general feature yet. Do a short spike, then decide.**

1. **Spike A: Bluetooth hands-free (2–3 days, Mac only, no phone code).**
   - A small macOS test app pairs with an Android phone as Hands-Free, answers a call, calls `transferAudioToComputer`, and checks for audio both ways in Core Audio.
   - If it works on macOS 14 and 26, F-23 becomes **"Build"**: about 2–3 weeks, works in Basic mode on all phones.
   - If it doesn't work, F-23 is **"Don't build"** for cellular calls.
2. **Spike B: Full-mode probe (half a day, optional).**
   - From the helper, log `isPstnCallAudioInterceptable()` and test the `voice-call-downlink` source on the owner's phones.
   - This tells us if a "Full mode, some phones" extra is real. We would not lead with it.
3. **VoIP calls via `CALL_REDIRECT_VOIP`** (Full mode, Android 13+): keep as a later research item. Users can already take those calls in the Mac's own WhatsApp/Meet apps.

**Rough size:** spikes 3–4 days in total. Building, if Spike A works: 2–3 weeks (pairing guide, HFP session, F-06 UI hookup, device routing, tests on the device matrix).

**What the user must decide:**
1. Is **Bluetooth pairing** (in addition to our Wi-Fi pairing) acceptable for this one feature?
2. Is **"phone quality" (8–16 kHz) audio** acceptable?
3. If Bluetooth doesn't work on modern macOS: drop F-23, or allow a **Full-mode-only, some-phones-only** version with a clear "may not work on your phone" label?
