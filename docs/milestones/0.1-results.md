# Milestone 0.1 results

Branch `milestone-0.1`. This file has two parts: checks that were run without a phone (with measured results), and checks the owner must run on a real phone and Mac (each with a procedure and a `PENDING` result line to fill in).

## Part 1: Measured without a phone

### Clean-clone build time

Target (PRD): a new contributor builds both apps in under 30 minutes.

Method: `git clone --branch milestone-0.1 <repo> <tmp>`, then the README "Build it" section followed literally, each step timed. `JAVA_HOME` was a JDK 21 and `ANDROID_HOME` pointed at the SDK (`android/local.properties` is gitignored, so a fresh clone needs one of the two, as the README says). protoc 4.36.2 was already installed on this machine, so the download step was not repeated.

| Step | Time | Result |
|---|---|---|
| `scripts/gen-proto.sh` | 43 s | ok |
| `python3 -I protocol/tools/make_vectors.py --check` | 1 s | ok |
| `swift test --package-path mac/Packages/AMKit` | 37 s | ok |
| `xcodegen --spec mac/project.yml` | under 1 s | ok |
| `xcodebuild ... build` (ad-hoc signed) | 49 s | BUILD SUCCEEDED |
| `./gradlew :app:assembleOssDebug` | 3 s | BUILD SUCCESSFUL (47 of 83 tasks from the Gradle build cache) |
| `scripts/interop-test.sh` | 10 s | all 5 cases passed |
| **Total** | **143 s (about 2.4 min)** | |

**Apple silicon, warm cache; Intel not timed.**

**Caveat: this is a warm-cache time.** Gradle (including its build cache), SwiftPM and the Android SDK were already on this machine. A first-ever build adds the Gradle distribution and dependency downloads, the swift-protobuf and swift-crypto checkouts, installing xcodegen, protoc, a JDK and the Android SDK. That is not measured here. The warm-cache time has no bearing on whether the 30 minute target holds for a first-time contributor on a slow link; it only shows the build steps themselves are short.

README steps that failed or needed guessing: none. Notes:
- The README uses `xcodegen --spec mac/project.yml` with no `--project`; it writes `mac/AndroidMirroring.xcodeproj` next to the spec, which is what the `xcodebuild` line uses. CI passes `--project mac`, which is equivalent.
- The Mac build ran on Xcode 27.1 (the README says "26 or later"). Xcode 26.x itself was not tried.

### Security spot checks (against `am-mac-sim`, not the Mac app)

Run from the clean clone. Loopback (`127.0.0.1`) was used, so these cover the TLS stack, not a second machine on the LAN.

**Interop cases 4 and 5: PASS.**
```
PASS  1 pair + connect
PASS  2 status
PASS  3 ring
PASS  4 stranger (pinned phone state, wrong certificate)
PASS  5 reused QR
interop: all 5 cases passed
```

**TLS 1.2 refused: PASS.** `am-mac-sim --identity protocol/testdata/identities/mac.p12 --state-dir <tmp> --port 0 --auto-confirm` (Bonjour on) listened on port 51082.
```
$ openssl s_client -connect 127.0.0.1:51082 -tls1_2 </dev/null
Connecting to 127.0.0.1
...error:0A00042E:SSL routines:ssl3_read_bytes:tlsv1 alert protocol version:ssl/record/rec_layer_s3.c:916:SSL alert number 70
CONNECTED(00000003)
---
no peer certificate available
...
SSL handshake has read 7 bytes and written 189 bytes
New, (NONE), Cipher is (NONE)
```
The server answered with a `protocol_version` alert (70) and no certificate.

**TLS 1.3 without a client certificate refused: PASS.**
```
$ openssl s_client -connect 127.0.0.1:51082 -tls1_3 </dev/null
depth=0 CN=AM Test Mac
verify error:num=18:self-signed certificate
CONNECTED(00000003)
...
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
...
...error:0A00045C:SSL routines:ssl3_read_bytes:tlsv13 alert certificate required:ssl/record/rec_layer_s3.c:916:SSL alert number 116
```
The handshake got as far as TLS 1.3 and the server then demanded a client certificate (alert 116, `certificate_required`) and closed. (The `self-signed` line is openssl's view of the server's test certificate; the app pins by fingerprint, so that is expected.)

**Bonjour contents: PASS.** Each `dns-sd` call was backgrounded and killed after 5 s.
```
$ dns-sd -B _anmirror._tcp local.
 Add  3  1 local.  _anmirror._tcp.  am-b1f2e1be
 Add  2 11 local.  _anmirror._tcp.  am-b1f2e1be

$ dns-sd -L am-b1f2e1be _anmirror._tcp local.
am-b1f2e1be._anmirror._tcp.local. can be reached at Phanis-MacBook-Air.local.:51082 (interface 11)
 r=583cc0775958230a v=1
```
The instance name is `am-` plus 8 hex characters, the TXT record holds only `v=1` and `r=` plus 16 hex characters (a rotating ID, not the device ID), and the port matches the sim's. Nothing else (no device name, no fingerprint) is advertised. (Since the final-review fixes the instance name is also re-randomised at every 15-minute epoch and on wake, per SPEC 1; the phone matches TXT `r`, not the name. Covered by a unit test, not re-run with `dns-sd`.)

**Cleanup:** the sim and both `dns-sd` processes were killed; `pgrep -fl "am-mac-sim|dns-sd|phone-sim"` printed nothing afterwards.

## Part 2: Owner-run checks

Time with a phone or wall stopwatch. "Connected" means the Mac menu shows the phone's name and a status line.

How fast "disconnected" shows (PRD F-02, SPEC 7; builder's call for 0.1, faster detection tracked for 0.9): **immediately when the connection closes** (app quit, Mac sleep/wake, phone app stopped); **within 75 s when the phone vanishes** (Wi-Fi off, out of range), because the Mac only notices a vanished phone by 75 s of silence.

### (h) Screen-off keep-alive (TOP RISK)

**This is the highest-risk check in 0.1. Run it first.** The phone keeps the connection alive with a ping every 30 s; Android may defer that in Doze when the screen is off and the phone unplugged, and the Mac drops a phone after 75 s of silence.

1. Phone connected, charger unplugged. Note the time.
2. Turn the phone's screen off and leave it untouched (face down, no charger) for **at least 30 minutes**.
3. Without waking the phone, open the Mac menu: it must still show the phone's name and "Connected".
4. Choose "Ring the phone": the phone must ring. Stop it from the Mac.
5. Note in the result whether the menu ever showed "Not connected" during the 30 minutes (open it a few times, without touching the phone).

Pass: after 30 minutes or more with the screen off and unplugged, the Mac still shows Connected and Ring phone works.

**If this fails, 0.1 is not done:** the keep-alive model needs a redesign (Mac-driven pings plus TCP keepalive, so an idle phone need not wake to send) before 0.1 is finished.

## Part 3: Owner device session, 2026-10-30

Phone: vivo V2558, Android 16. Mac: Release build 8cc13a5 (ad-hoc signed), installed as the only copy in /Applications.

- **Pairing:** PASS by QR code (after forgetting the old `am-mac-sim` pairing). The phone shows "Connected to <Mac>", and the Mac holds the TCP session.
- **Problems found while setting up (to fix before release):**
  1. On launch, the Keychain "Always Allow" prompt can sit behind other windows. The app does not start listening until the prompt is answered, so it looks as if the app never opens. Ad-hoc builds prompt again after every rebuild; a signing team fixes that.
  2. On a MacBook with a notch, the menu-bar icon is hidden when the menu bar is full, and opening the app again did nothing, so the app could not be reached at all. Fix tried in the test build: `applicationShouldHandleReopen` opens the pairing window (not connected) or the Phone window (connected). Not in the product yet; it is a 0.5 follow-up.
  3. macOS notification permission: phone notifications reached the Mac app but were not shown until the owner turned on Android Mirroring in System Settings › Notifications. The app had no entry there before, so the permission prompt was never seen.
- **(h) Screen-off keep-alive:** NOT RUN YET. A forced-Doze pass over USB was stopped after about 1 minute because the phone was in use (the screen was on). Still connected at that point. The real 30-minute unplugged run is still to do.
- **0.2 notifications, basic:** a test notification posted on the phone showed on the Mac once permission was on. Latency (0.2 check (a)) not measured yet.
