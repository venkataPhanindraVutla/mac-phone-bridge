# Milestone 0.3 results

Branch `milestone-0.3`. Like the 0.2 file, this has two parts: checks that were run without a phone (with measured results), and checks the owner must run on a real phone and Mac (each with steps and a `PENDING` result line to fill in). It then lists the copy the implementers wrote for the owner to review, the decisions made during the build, and the known limitations.

Milestone 0.3 covers sharing and files: the shared clipboard (text), sending files and links in both directions, transfer progress and cancel, screenshots sent to the Mac, recent photos on the Mac, browsing and managing the phone's files from the Mac (Files tab), and, in the Full build, the phone in Finder's sidebar and a "Send to Phone" Share menu item.

### Log audit

The brief: no log call may interpolate a name, path or text variable. Checked by listing the 97 non-test Kotlin and Swift source files changed since 0.2 (`git diff --name-only 02283a6..HEAD`, minus test files and the phone-sim tool's output), then grepping them for `Log.`, `log(`, `log.`, `Logger`, `print`, `println` and `NSLog`, and reading each hit.

- Every log line interpolates only transfer and request IDs, counts, sizes, durations, rates, enum names (outcomes, reasons, failure kinds), fixed literals, or an exception's class name (`e.javaClass.simpleName`, `type(of: error)`, `NSError.code`).
- The helpers that wrap background work (`launchQuietly`, the photos and browse runners) log a fixed literal plus the exception's class, never its message (a message could carry a URI). All call sites pass literals such as `"browse: add folder"`.
- Mac logs that print a failure (`String(describing: failure)`) print a `TransferFailure`, which is an enum of transfer or browse outcome codes with no associated names.
- Two Mac lines (`AppModel.swift:508` and `:606`) log the pairing URI and code. They sit under the Debug-only logger (`category: "debug"`) from 0.1 and are the documented Debug-build behaviour in the README, not 0.3 code.

Result: no log call in the 0.3 sources interpolates a file name, path, URL, clipboard text or photo metadata (PASS).

## Part 2: Owner-run checks

Setup for all of them: Mac running the Mac app built from this branch's HEAD **in the Release configuration** (README "Build it"; Debug builds carry development-only hooks). The phone has the debug APK installed, both on the same Wi-Fi network, paired. On the phone, turn on each feature as its check needs it (the home screen asks for each permission when its switch is turned on). For the Finder checks (h1 to h6) the Mac app must be the Full build.

Have ready: a stopwatch, a 1 GB test file on the Mac and one on the phone (`mkfile 1g ~/Desktop/1g.bin` on the Mac; on the phone, a large video or a file copied there), a second Android phone is not needed. Note the router, the Wi-Fi band and the phone model once, and reuse them below.

### (a) 1 GB both ways over 5 GHz Wi-Fi

Target: at least 20 MB/s each way.

1. Both devices on the same 5 GHz network (not 2.4 GHz). Phone close to the router. File sharing is on in the phone app ("Share files" row) and the Mac menu shows the phone's name.
2. Mac to phone: choose "Send File to Phone…" in the menu and pick the 1 GB file (or drop it on the Phone window's Send tab). Watch the Mac menu line "Sending … · n%" and the phone's "Receiving …" notification.
3. When it finishes, the phone shows "Saved to Download/Android Mirroring" and the file in the Files app has the right size. On the Mac read the rate from the log:
   ```sh
   log show --last 5m --predicate 'subsystem == "io.github.anmirror.mac" AND category == "transfer"' --info | grep "MB/s"
   ```
   The line reads `<id> <bytes> B in <ms> ms = <rate> MB/s`. Write down the rate.
4. Phone to Mac: from the phone's gallery or Files app, share the 1 GB file to "Send to Mac". It lands in `~/Downloads` on the Mac. Read the same log line for the rate.
5. The first time a file arrives, macOS may ask whether Android Mirroring may access the Downloads folder. Click Allow and write down that it asked, and whether the file was saved after you allowed it.
6. Check the file's hash on the Mac against the original (`shasum -a 256 <file>`); they must match.

### (b) Interrupted transfers and cleanup

Expect a clear failure on both sides and no partial file left anywhere.

1. **Wi-Fi off mid-transfer.** Start a 1 GB file Mac to phone. At about 30 %, turn Wi-Fi off on the phone. Within about 30 s both sides show a failure: the Mac says "Couldn't send <name>. The connection was lost." and the phone's notification says "Couldn't receive <name>" with the same reason. Turn Wi-Fi on again. Check `Download/Android Mirroring` in the phone's Files app (and the Downloads app): no partial file and no half-size file. Repeat phone to Mac: after the failure `~/Downloads` has no `.<uuid>.part` file (`ls -a ~/Downloads | grep part`) and no half-size file.
2. **Mac sleep mid-transfer.** Start a large file in each direction in turn and put the Mac to sleep with the lid or the Apple menu. Wake it. Expected: the transfer is shown as failed on both sides (the phone shows "Couldn't ..."), the partial file is gone, and a new transfer works after the phone reconnects. Nothing resumes by itself.
3. **Cancel on the Mac.** Start a 1 GB send and click Cancel next to the menu's transfer line (or in the Send tab). The phone's notification goes away and no file is left. Repeat phone to Mac.
4. **Cancel on the phone.** Tap Cancel on the phone's "Receiving …" or "Sending …" notification. The Mac shows the transfer as ended and no partial file is left. (A cancel the user did on the phone adds no result notification on the phone; the Mac's line reads "Cancelled.")
5. **Leftover rows after a crash.** While a Mac-to-phone transfer is running, force-stop the phone app (Settings, Apps, Android Mirroring, Force stop). Open the app again and let it reconnect. Then look in the Files app for any "pending" or hidden download in `Download/Android Mirroring`: the app's start-up sweep must remove leftovers of its own.

### (c) Clipboard

1. Phone connected; "Share clipboard with your Mac" is on in the phone app, and "Send Mac clipboard to the phone" is on in the Mac Settings.
2. **Mac to phone, under 1 s.** Copy a sentence on the Mac. Start a stopwatch and stop it when the text pastes into any phone text field. Do it five times with different text. Under 1 s passes.
3. **Phone to Mac: three routes.**
   - Quick Settings tile "Send clipboard to Mac": copy text on the phone, pull down the shade, tap the tile (add it from the tile editor first). The phone toasts "Sent to <Mac name>" and the text pastes on the Mac.
   - The persistent notification's "Send clipboard" action: same result.
   - Share sheet: share text from a notes app to "Send to Mac". A notification "Copied from <phone>" appears on the Mac and the text is on the Mac's clipboard.
4. **Phone-side focus and API levels.** The tile and the notification action open a transparent screen to read the clipboard (Android only lets the app in front read it). On Android 10 to 12, 13 and 14 or later, write down for each whether the clipboard is read and sent correctly, and whether the screen flickers or the tile stays active. On Android 14 and later the tile from a locked phone asks you to unlock first: check that it then sends.
5. **Toasts.** Clear the clipboard and tap the tile: "Clipboard is empty". Copy a very long text (over 256 KB, for example a text file pasted whole) and send it: "Text is too long to send". Send the same text twice from the phone with no Mac change in between: "Your Mac already has this text". Turn the phone's clipboard switch off and tap the tile: the tile is greyed out; if you can tap it, it says "Clipboard sharing is off" and does not read the clipboard.
6. **Password managers.** Copy a password from 1Password, Bitwarden or the macOS Passwords app. It must **not** arrive on the phone. (Check with a phone text field: paste must not give the password.) Also copy an ordinary text right after: that one must arrive.
7. **No echo.** Copy "A" on the Mac, let it arrive on the phone, then do nothing: the phone must not send "A" back (watch that the Mac gets no "Copied from" notification and the Mac clipboard does not change). Then send "B" from the phone: it arrives on the Mac and is not sent back to the phone. Re-copy "A" on the Mac afterwards: it is sent again (a deliberate re-copy is not dropped).
8. **Mac menu.** "Send Clipboard to Phone" in the menu sends the current text to the phone. With the Mac clipboard empty it says "The clipboard is empty."

## Decisions made during the build

Rulings made by the controller while the build ran, one line each: what, and why.

- **R1: File-name clashes ignore upper and lower case, on both sides.** The Mac and Android shared storage don't tell "Photo.jpg" and "photo.jpg" apart by default, so one file would silently replace the other. Cost if wrong: an unneeded "(1)" on a case-sensitive disk.
- **R2: The Mac side of file sending was built at the same time as the phone side, and the cross-check between the two was added in a short follow-up.** The cross-check needs the phone's engine, which did not exist yet. Cost if wrong: one extra small task.
- **R3: The clipboard waited until the Mac side of file sending was merged.** Both needed the same message-routing hook and would have invented it twice.
- **R4: Sending from the Mac fails at once when no phone is connected, or the phone doesn't take files; nothing queues across sessions.** The protocol forbids sending messages for features the phone didn't list, and a queued drop could reach a different phone. The user re-drops after a reconnect.
- **R5: One shared set of file messages carries sending, browsing, screenshots and photos, and each use is gated by its own feature.** Browsing writes must keep working when the user keeps plain file sharing off.
- **R6: The clipboard echo rule keeps one fingerprint per side, "the text the other side has now."** The first plan (remember only the last received text) dropped a deliberate re-copy, which broke the one-second paste goal. The fingerprint is cleared on disconnect.
- **R7: With the phone connected and the clipboard switch off, the tile is unavailable and the clipboard is never read.** The old "Not connected" toast was false, and the app should not read what the user told it not to share.
- **R8: Text shared to "Send to Mac" goes straight from the share intent.** The text is already there, so there is no clipboard read and no focus trick.
- **R9: The phone shows at most one ongoing transfer notification per direction, with "N more waiting," plus one replaced result notification per direction.** One notification per file hit Android's update-rate limit and 50-notification cap, so a 50-file share would have lost its Cancel buttons.
- **R10: The Mac hides refusals the user didn't start from its transfer list and "last failure" line.** The user can't act on them, and the phone shows its own failure.
- **R11: The Mac menu shows at most one active transfer per direction plus "N more waiting"; the full list is in the Send tab.** Fifty menu lines pushed Hang up and Quit off the screen and don't refresh while open.
- **R12: Automatic phone transfers (screenshots, photos, browse answers) are left out of the phone's transfer notifications.** The user didn't start them there, and a screenshot a minute would churn the shade. Cost: a failed screenshot send shows only on the Mac.
- **R13: Received screenshots don't appear as menu lines on the Mac.** They finish in a second and the notification is the interface. They stay in the Send tab, and a failed one still counts in "Couldn't receive."
- **R14: A screenshot folder is any folder whose name contains "screenshot", ignoring case.** Some makers save to "Screenshot" (singular).
- **R15: Request timeouts live in the Mac's engine and run only while no receive is in progress.** The phone sends one thing at a time, so a busy receive means the phone is alive. This stops a photo fetch behind a big file from falsely timing out.
- **R16: The phone's transfer notifications also skip browse traffic.** Those transfers are driven from the Mac's Files tab, and the "Saved to Download" wording would be wrong for them.
- **R17: The Mac asks the phone for at most 8 file reads at once and queues the rest.** The phone allows 64, and a big multi-select drag from Finder could otherwise exceed that.
- **R18: Share-menu items remember which phone they were for.** They are sent only to that phone, dropped if it is forgotten, and dropped after 24 hours. This keeps R4's rule for the one path that legitimately queues across sessions.
- **R19: Finder (File Provider) errors follow Apple's documented contract, not the plan's.** The plan's error would make Finder retry forever; refusals, "unchanged" answers and "not synced" answers are used instead.
- **R20: Cancelling in Finder reaches the app, through one added call.** Without it, a cancelled download kept running and kept one of the 8 read slots (R17) and the link.
- **R21: Share-menu items blocked only because a feature is off are kept, up to 24 hours.** A file or text is dropped only if it is gone or unreadable, so the sending side never loses things silently. Cost: a share made long before turning the feature on is sent late.

## Known limitations in 0.3

- No resume: an interrupted transfer fails and has to be sent again.
- No drop onto the menu-bar icon: the menu-bar item can't take drops. Use the Phone window's Send tab, the menu's "Send File to Phone…", or the Share menu in the Full build.
- Folders are not sent or downloaded: dropping a folder says "Folders can't be sent yet. Send the files inside instead.".
- The Share menu name is fixed ("Send to Phone"), not the phone's name.
- Only text goes on the clipboard (images are 1.x).
- Screenshots and photos taken while the phone is disconnected are not sent later.
- All files access is only on Android 11+; Android 10 browses picked folders only.
- On macOS 14 the App Group container is not exclusive to the app's team, so another process of the same user could plant a Share-menu item for the app to send. The risk is low: the worst case is an unwanted link or text notification on the phone.
- Finder folder listings don't refresh by themselves: a change made on the phone (or on the Mac side) shows only when Finder lists the folder again. The Files tab re-lists on request.
- Overwriting a file in a picked folder (the system folder picker, "SAF") is not atomic. The old file is moved aside, the new one is renamed into place, and the old one is deleted. If something fails in between, a visible copy of the user's file always remains, and a crash can leave a hidden `.<uuid>.part` that is never listed and never cleaned up. All files access writes don't have this limit.
- A screenshot or photo sent in the background doesn't show on the phone: no notification and no result line there (R12), so a failure shows only on the Mac.
- The phone app's transfer notifications show no per-file detail beyond the active one and the counts (R9).
- A link with a non-ASCII host (such as `café`) is treated as text on the Mac but as a link on the phone.
- Time-of-check races: the phone's checks that a folder was not swapped for a link are best effort, since Android's Java API has no `openat`. Nothing is written outside a chosen folder, but a swap in the instant before the final rename is not caught.
- A hash is checked on every transfer, but extra bytes after the end of a file can only be noticed best-effort on a TLS link.
- Not exercised without hardware: the Full build's signing, the File Provider, the Share extension, and everything in the owner checks above.
