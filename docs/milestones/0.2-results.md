### Release build has no debug strings

The development hooks read environment variables such as `AM_DEBUG_BEGIN_PAIRING` and `AM_DEBUG_AUTO_CONFIRM`, only under `#if DEBUG`. Find the built apps with `xcodebuild -project mac/AndroidMirroring.xcodeproj -scheme AndroidMirroring -configuration Release -showBuildSettings | grep BUILT_PRODUCTS_DIR` (`<Release>` below is that directory; `<Debug>` is the same path with `Debug` at the end). Check, with a positive control:
```
$ strings -a "<Release>/Android Mirroring.app/Contents/MacOS/Android Mirroring" | grep -c AM_DEBUG
0
$ find "<Release>/Android Mirroring.app" -type f -exec strings -a {} + | grep -c AM_DEBUG
0
$ strings -a "<Debug>/Android Mirroring.app/Contents/MacOS/Android Mirroring.debug.dylib" | grep -c AM_DEBUG
2
```
The Release app, and every file in its bundle, has no `AM_DEBUG` string (PASS). The Debug build does have them, in `Android Mirroring.debug.dylib`, so the search works. (The Debug stub executable itself shows 0; the code lives in the dylib.)

## Part 2: Owner-run checks

Setup for all of them: Mac running the Mac app built from this branch's HEAD **in the Release configuration** (README "Build it": `xcodebuild ... -configuration Release`; Debug builds carry development-only hooks and are not what users run), phone with the debug APK installed, both on the same Wi-Fi network, paired. The app on the phone must have been given the permissions it asks for (notifications, notification access, contacts, call-log access and phone access where asked). Where a check needs a second phone, use a phone (or a landline) that can call or message this phone's number.

Two things to have ready: a way to send messages to the phone (a second phone with WhatsApp or SMS, or a messaging app on a tablet), and a stopwatch (a phone or wall clock is fine).

### (a) Notification latency

Target: each of ten notifications appears on the Mac in under 1 s after it appears on the phone.

1. Phone connected; the Mac menu shows the phone's name. In the Mac app's Settings, "Show phone notifications" is on.
2. Start a screen recording on the Mac (QuickTime Player, File, "New Screen Recording"), with the phone held in front of the Mac's camera or next to the screen so that you can see the phone's screen on the recording. (Alternatively use the phone's own screen recorder and the Mac recording together, and line them up by the moment you send the message.)
3. From the second phone or a messaging app, send ten messages to this phone, about 10 s apart, from one app with its notifications turned on.
4. Measure each from the recording: step through it frame by frame (QuickTime: the left and right arrow keys step one frame; a 30 fps recording is about 33 ms a frame). Count the frames from the one where the notification first appears on the phone to the one where the banner first appears on the Mac. Under 30 frames at 30 fps (1 s) passes. Write each one down.
5. Rough fallback if recording is not possible: a stopwatch started when the notification appears on the phone and stopped when the Mac banner appears. Human reaction time is about 0.2 to 0.3 s, so only trust this for clear passes (well under 1 s) or clear fails (over 1.5 s).

## Known limitations in 0.2

- No call-waiting swap or reject from the Mac: a second call that rings during a call shows its panel with Close only.
- A reply typed on the Mac while the phone is not connected is not queued; the Mac says "Your phone isn't connected. Nothing was sent."
- The call timer on the Mac restarts at 00:00 after a reconnect during a call.
- Answer can be unavailable in builds without the answer-calls permission (`ANSWER_PHONE_CALLS`).
